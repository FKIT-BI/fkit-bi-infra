# Инициализирующий промпт для FKIT BI

Запускай этот промпт из каталога `fkit-bi-infra`. Предоставь ссылку на GitHub-организацию, IP и пользователя Dev, SSH-ключ и GitHub-токен через безопасный механизм или локальные файлы вне git. Агент должен создать репозитории, разместить Secrets/Variables в организации и проверить реальную первую выкладку.

---

Ты — инженер, который инициализирует многорепозиторный проект FKIT BI. Твоя задача — создать минимальные рабочие каркасы четырёх репозиториев, настроить BMAD и GitHub Actions, создать репозитории в указанной GitHub-организации, разместить настройки и секреты на уровне организации, запушить начальное состояние и развернуть каркасы на предоставленном Dev-стенде. Выполни работу до проверенного результата, а не ограничивайся планом или рекомендациями.

## Входные параметры

- `GITHUB_ORG_URL = <ссылка на организацию компании в GitHub>` — обязательная целевая организация. Определи из ссылки `GITHUB_OWNER` и проверь его через GitHub API. Не угадывай владельца по текущему аккаунту. Если дана ссылка на GitHub Project или репозиторий, проверь организацию-владельца; при неоднозначности уточни только её.
- `WORKSPACE_ROOT = <путь или AUTO>` — общий каталог с четырьмя соседними репозиториями. При `AUTO` определи по текущему каталогу infra.
- `DEV_HOST = <IP Dev-стенда>`, `DEV_SSH_USER = <имя пользователя>` — предоставляются пользователем.
- `DEV_SSH_PORT = <порт или 22>`, `DEV_DEPLOY_PATH = <путь или /opt/fkit-bi>`, `DEV_PUBLIC_URL = <URL или http://IP:согласованный-порт>` — проверь пригодность значений и задокументируй выбранные настройки.
- `DEV_SSH_PRIVATE_KEY_PATH = <путь к предоставленному SSH-ключу вне git>` либо ссылка на доступный агенту защищённый credential. Passphrase при наличии передаётся отдельно безопасным способом.
- `GITHUB_TOKEN_SOURCE = <защищённый credential / environment variable / путь вне git>` — предоставленный GitHub-токен с широкими правами для создания репозиториев и администрирования Actions Secrets/Variables организации. Проверь фактические права, SSO-авторизацию и пригодность токена для необходимых операций, а не предполагай их по описанию «максимальные права».
- `DEV_SSH_HOST_FINGERPRINT = <если предоставлен>` — используй для проверки ключа сервера; иначе найди доверенный источник в существующей SSH-конфигурации или запроси только подтверждение первого подключения. Один ssh-keyscan без проверки не устанавливает доверие.
- Значения секретов в этот промпт, документы, git, вывод команд и итоговый отчёт не записывай.

Создание приватных репозиториев, обычный push, создание проектных Secrets/Variables в организации и первоначальная установка на указанный Dev входят в задачу. Не запрашивай повторное подтверждение этих действий. Не изменяй настройки посторонних проектов компании. Если обязательный параметр или доступ отсутствует, продолжай независимую работу и запроси только то, что действительно блокирует следующий шаг.

## Принятые решения

Названия строго следующие:

| Репозиторий | Ответственность |
|---|---|
| `fkit-bi-analytics` | Java 21 / Spring Boot: структура оборудования, CRUD, чтение телеметрии, аналитика, инциденты; владелец миграций общей PostgreSQL |
| `fkit-bi-generator` | Java 21 / Spring Boot: API управления генерацией, сценарии, запуски; прямая пакетная запись телеметрии в PostgreSQL через JDBC |
| `fkit-bi-web` | Web-клиент: структура оборудования, мониторинг, история, инциденты, управление генератором; дальнейшая реализация за фронтенд-разработчиком |
| `fkit-bi-infra` | Общий контекст и межсервисные задачи BMAD; Docker Compose, прокси, конфигурация окружения, общие скрипты доставки |

Доменная структура: предприятие → производственная линия → станок → компоненты и инструменты; параметры оборудования, измерения, простои, аварии, скорость и ручные сведения сотрудников об инцидентах.

Для демо: два Spring-приложения, web и одна PostgreSQL. Генератор пишет исходные измерения напрямую в БД по согласованному контракту; analytics читает их и управляет структурой, аналитикой и инцидентами. Kafka и ETL отложены. В генераторе предусмотрен интерфейс `TelemetrySink` для будущей замены адаптера записи.

Сейчас настраиваем только Dev. Каждый push в `develop`, включая результат merge pull request, автоматически запускает сборку и доставку соответствующего приложения. Релизы, согласованный набор стабильных версий, ручное обновление manifest версий и Prod-пайплайны в этот этап не входят. Для приложений на Dev достаточно обновляемого тега `dev`; SHA коммита сохраняй в metadata и логах для диагностики.

## 1. Проверь окружение и сохрани существующую работу

Прочитай доступные `AGENTS.md`, изучи текущую infra, git status, remotes, ветки и соседние каталоги. Проверь Git, GitHub CLI либо другой доступный GitHub-интерфейс, Docker, Java 21, Node.js и зависимости выбранного способа установки BMAD.

Если infra уже существует, используй её. Если остальные репозитории уже созданы, продолжай в них. Не создавай дубликаты, не перезаписывай пользовательский код, не меняй чужие remotes без необходимости. Не выполняй force push, reset пользовательских изменений и удаление данных. Не инициализируй один git-репозиторий над всем workspace и не добавляй соседние проекты в git infra.

Создай недостающие каталоги как соседние самостоятельные git-репозитории. По умолчанию remote-репозитории приватные. Создай `main` и `develop` с исходным каркасом; автоматическая доставка действует только для `develop`. Существующие настройки веток сохраняй, если они не противоречат задаче.

## 2. Подготовь минимальные рабочие каркасы

Это bootstrap проекта: бизнес-функциональность пока не реализуй. Репозитории должны содержать достаточно файлов, чтобы собираться, проверяться и принимать дальнейшие изменения.

В каждом репозитории создай README, `.gitignore`, `.editorconfig`, локальный `AGENTS.md`, необходимые примеры конфигурации, документацию запуска и GitHub workflow. В README укажи назначение, владельца ответственности, команды проверки и связи с остальными репозиториями.

Для analytics и generator:

- Java 21, согласованная стабильная версия Spring Boot с официально подтверждённой поддержкой Java 21, Maven Wrapper и воспроизводимая сборка.
- Минимальный запускаемый Spring Boot application и Actuator health; небольшой содержательный smoke test запуска.
- Dockerfile, `.dockerignore`, конфигурация через environment variables; конфигурация подключения к PostgreSQL.
- В analytics — каталог и конфигурация Flyway, документированный единый порядок миграций. Пока достаточно технического каркаса; полную доменную схему не проектируй молча в этой задаче.
- В generator — минимальные границы модулей управления запуском, движка и `TelemetrySink`; JDBC-адаптер можно оставить документированным каркасом. Генератор не запускает миграции общей БД самостоятельно.
- Проверь возможность запуска обоих приложений в окружении Compose. Не маскируй обязательную зависимость от БД отключением проверок здоровья.

Для web сохрани существующий стек. Если проекта ещё нет, подготовь только минимальный каркас React + TypeScript + Vite с lockfile, build/typecheck и простой стартовой страницей FKIT BI. Это стартовая заготовка для фронтенд-разработчика, без реализации предметных экранов. Добавь конфигурацию адресов analytics и generator, Dockerfile для выдачи статической сборки и проверку доступности HTTP. Предпочти относительные API-пути через прокси.

В infra подготовь:

- Compose для PostgreSQL, analytics, generator, web и прокси; постоянный volume PostgreSQL.
- `.env.example` без реальных секретов, настройки портов, маршрутов API и healthcheck.
- Скрипты проверки конфигурации, первоначального запуска инфраструктуры, доставки отдельного сервиса и проверки его здоровья.
- Документы архитектуры, контракта общей БД, процесса разработки, доставки Dev и восстановления после неуспешной выкладки.
- Настройки БД и пароли на сервере; исключи их попадание в git. Обычный деплой не должен удалять volume или пересоздавать данные.

## 3. Настрой BMAD и историю задач

Установи и настрой BMAD по официальной документации для используемого агентского инструмента. Проверь фактическую версию и доступные команды; зафиксируй одну согласованную версию для всех репозиториев. Не выдумывай команды и не создавай фиктивные файлы вместо рабочей установки.

Обеспечь два режима работы: общая работа из infra с доступом к соседним репозиториям и локальная работа из конкретного сервиса. Если выбранная версия требует setup на уровне workspace для межрепозиторной работы, настрой его, сохранив общие документы и задачи под git infra; опиши воспроизводимый bootstrap нового рабочего места.

Общий источник требований и архитектурных решений находится в infra. Сервисные репозитории содержат ссылки на этот контекст и собственные правила, планы реализации, результаты проверок и историю завершённых задач. Не создавай четыре независимо редактируемые копии общего документа. Локальный `AGENTS.md` обязан объяснять, как получить и прочитать общий контекст, включая случай, когда infra ещё не клонирована рядом.

Для межсервисной задачи используй общий идентификатор и связанные локальные задачи. В infra фиксируй зависимости и сводный статус; в сервисном репозитории — что сделано, когда, как проверено и какими коммитами/PR доставлено. Сохраняй завершённые планы. Статусы реализации, merge и фактического деплоя различай.

Создай начальную задачу bootstrap и зафиксируй реальные результаты этой работы. Добавь краткие инструкции запуска планирования, реализации, review и обновления статуса для установленной версии BMAD. Настрой правила чтения контекста явно: агенту недостаточно просто увидеть ссылку.

BMAD используется разработчиками и агентами при работе над задачами. Не запускай автоматическую генерацию или изменение бизнес-кода через GitHub Actions на каждом push.

## 4. Создай GitHub Actions в каждом репозитории

Workflow должны лежать в `.github/workflows/` соответствующего репозитория и быть настоящими, синтаксически корректными pipeline, а не шаблонами с несуществующими командами.

Поведение для analytics, generator и web:

1. Pull request в `develop`: проверки и сборка без публикации образов и деплоя.
2. Push в `develop`: проверки → сборка Docker-образа → публикация в GHCR с тегом `dev` → автоматическая доставка этого приложения на Dev → healthcheck.
3. Дополнительный `workflow_dispatch` допускается для повторного запуска, но не является обязательным шагом обычной доставки.

Merge обрабатывается событием push в develop: не дублируй выкладку отдельным событием закрытия pull request. Публикацию выполняй после успешных проверок. Используй явные permissions; для публикации связанного GHCR-пакета предпочтителен `GITHUB_TOKEN` с `packages: write`. Учитывай нормализацию имени GHCR namespace в нижний регистр.

В infra сделай проверки Compose, shell-скриптов и workflow. Push в её develop применяет изменения окружения через отдельный infra deploy. Infra не собирает заново образы приложений.

Общие deployment-скрипты принадлежат infra. Сервисные workflow должны получать их явно: checkout infra с необходимым read-доступом либо другой проверенный механизм. На GitHub runner соседние репозитории сами собой не появляются. Если infra приватная, настрой доступ и документируй его; не рассчитывай на автоматический межрепозиторный доступ `GITHUB_TOKEN`.

При доставке приложения обновляй только выбранный сервис и необходимые ему зависимости. При доставке analytics применяй миграции один раз до запуска новой версии; при ошибке миграции останови этот деплой. Для общей БД сохраняй одного владельца миграций.

Сборки разных репозиториев могут работать параллельно. Операции изменения стенда сериализуй общей блокировкой на Dev-сервере: GitHub concurrency не является межрепозиторной блокировкой. Обеспечь корректность обновляемого тега `dev`: упорядочи публикацию и доставку одного сервиса, учитывай устаревшие запуски, чтобы поздно завершившаяся старая сборка не перезаписала новую. Не прерывай уже начатые миграции или обновление контейнеров простым cancel-in-progress. Записывай фактический commit/image ID и результат доставки для диагностики, без введения процесса стабильных релизов.

SSH known_hosts формируй на основании проверенного ключа сервера. Не отключай проверку SSH host key. Секреты не выводи в логи.

## 5. Размести Secrets/Variables в GitHub-организации и подключи Dev

Пользователь предоставляет GitHub-токен, SSH-ключ, IP и пользователя Dev. Основной результат этого этапа — настроенная и проверенная доставка на настоящий стенд. Не останавливайся на инструкции «добавьте секреты вручную», если предоставленные права позволяют выполнить это самому.

Создай настройки на уровне организации GitHub, в Actions Secrets and variables. Доступ предоставь только четырём репозиториям FKIT BI через selected repositories. Используй проектный префикс `FKIT_BI_`, чтобы не затронуть настройки других проектов компании. Перед записью проверь существующие имена и политики; не удаляй чужие секреты, не перезаписывай неожиданные конфликты молча.

| Название | Где хранить | Назначение |
|---|---|---|
| `FKIT_BI_DEV_SSH_PRIVATE_KEY` | Organization Actions Secret | Содержимое предоставленного приватного SSH-ключа, с сохранением переводов строк |
| `FKIT_BI_DEV_SSH_PASSPHRASE` | Organization Actions Secret, при наличии | Passphrase ключа; workflow должен поддерживать его через корректную SSH-настройку |
| `FKIT_BI_GITHUB_TOKEN` | Organization Actions Secret | Предоставленный токен для межрепозиторного доступа и чтения приватных GHCR-образов, если эти операции требуют его |
| `FKIT_BI_DEV_POSTGRES_PASSWORD` | Organization Actions Secret | Пароль PostgreSQL для нового Dev-окружения; существующий пароль и данные сохраняй |
| `FKIT_BI_DEV_HOST` | Organization Actions Variable | IP Dev-стенда |
| `FKIT_BI_DEV_SSH_USER` | Organization Actions Variable | Пользователь SSH |
| `FKIT_BI_DEV_SSH_PORT` | Organization Actions Variable | Порт SSH |
| `FKIT_BI_DEV_DEPLOY_PATH` | Organization Actions Variable | Каталог установки |
| `FKIT_BI_DEV_PUBLIC_URL` | Organization Actions Variable | Проверяемый адрес web, при отсутствии домена — IP и порт |
| `FKIT_BI_DEV_SSH_KNOWN_HOSTS` | Organization Actions Variable | Проверенная запись публичного host key; для нестандартного порта учитывай формат `[host]:port` |
| `FKIT_BI_GHCR_USERNAME` | Organization Actions Variable | Имя аккаунта, соответствующее токену для docker login; не подменяй его автоматически названием организации |
| `FKIT_BI_DEV_DEPLOY_ENABLED` | Organization Actions Variable | `true` после успешного preflight, для автоматической доставки из develop |

Предоставленный GitHub-токен разрешено использовать для bootstrap и сохранить как проектный organization secret для необходимых CI-операций. Если отдельно предоставлен runtime-токен, используй его в workflow вместо административного. Для публикации образов в своём репозитории по-прежнему предпочитай встроенный `GITHUB_TOKEN` с нужными permissions. Не создавай дополнительные PAT, не меняй существующие credentials и не публикуй секреты без необходимости.

Записывай секреты через API/CLI с передачей значения через stdin, защищённый файл или credential-механизм. Не включай значение в командную строку, git remote URL или shell tracing. Проверяй результат по именам и политикам доступа, а не попыткой прочитать секрет обратно. Для нового окружения сгенерируй стойкий пароль БД, сохрани его в organization secret и передай в защищённую серверную конфигурацию; обычные CI новых сервисов не должны перегенерировать пароль.

Проверь, что тариф и политики организации разрешают использование organization secrets/variables её приватными репозиториями. Широкие права токена не отменяют ограничений тарифа. Если организация запрещает нужную операцию, явно сообщи конкретный блокер и продолжай остальные разрешённые шаги; не переноси настройки в repository scope молча.

На Dev проверь SSH, права на каталог, доступ к Docker/Compose, доступ к GHCR и пригодность выбранных портов. На чистом выделенном стенде установи необходимые Docker/Compose средствами ОС, если их нет и у предоставленного пользователя есть разрешённые права. Существующие приложения и данные сохраняй; не отключай firewall и не занимай используемые порты без проверки.

Настрой получение private GHCR-образов сервером: credentials передавай защищённо и используй docker login с password-stdin; не предполагай, что `GITHUB_TOKEN` runner автоматически доступен серверу. Backend runtime получает пароли из защищённой серверной конфигурации, подготовленной из Secrets; минимальные права на файлы, отсутствие секретов в git и логах обязательны.

До подключения держи `FKIT_BI_DEV_DEPLOY_ENABLED=false` как техническое состояние bootstrap. После настройки доступов и preflight включи `true` сам, запусти или повтори первые workflow и проверь полную выкладку. Это однократная настройка, а не ручной шаг перед каждым push.

При выключенном параметре workflow summary явно сообщает, что деплой отключён; при включённом отсутствие обязательных настроек завершает preflight ошибкой до изменения сервера. Не используй прямое обращение к secrets в неподдерживаемом GitHub `if`: проверяй наличие через допустимый env/preflight механизм. CI проверяет реальный каркас независимо от credentials Dev.

Для первого старта отдели запуск PostgreSQL/прокси от запуска приложений, образы которых ещё не опубликованы. После появления всех образов запусти приложения, проверь health обоих backend, web по HTTP и маршрутизацию API. В финальном отчёте раздели: CI проверен, образы опубликованы, секреты/variables настроены, деплой фактически выполнен и проверен. При реальном блокере оставь готовые каркасы и workflow, но не называй bootstrap полностью завершённым.

## 6. Создай и запушь GitHub-репозитории

Проверь целевую организацию и уже существующие remote-репозитории. Создай недостающие приватные репозитории и настрой origin. После создания репозиториев назначь им доступ к organization Secrets/Variables до push, который должен запустить доставку. Сделай отдельные осмысленные коммиты в каждом проекте и запушь main/develop. Опубликуй infra и необходимые зависимости до workflow, которые обращаются к ней. Проверь доступность GitHub Actions и права чтения общих компонентов.

Перед push проверь отсутствие секретов, артефактов сборки и соседних репозиториев в staged-файлах. После push проверь remote SHA и результаты начальных Actions. Исправь обнаруженные ошибки каркасов и workflow, повторно запушь изменения. Недоступные административные настройки компании явно перечисли как блокеры, а разрешённую работу доведи до конца.

## 7. Проверки и итоговый результат

Проверь локальные сборки backend и web, Docker build, Compose config, shell-скрипты и GitHub workflow. Выполни минимальный запуск каркасов с PostgreSQL и проверь health/HTTP. Не ограничивайся проверкой наличия файлов. Если реальный Dev доступен, дополнительно проверь фактическую выкладку.

Критерии завершения:

- Четыре самостоятельных репозитория с правильными названиями созданы или корректно переиспользованы и запушены в указанную организацию.
- Начальные каркасы собираются; предусмотрен рабочий workflow для каждого репозитория.
- Настроен проверенный BMAD с общим контекстом в infra и локальной историей задач.
- Organization Secrets/Variables с проектными именами созданы, политики доступа к четырём репозиториям проверены, значения секретов нигде не раскрыты.
- Push в develop автоматически публикует и доставляет соответствующий сервис; первые выкладки реально выполнены и прошли проверку на предоставленном Dev.
- Есть инструкции нового рабочего места, схема Secrets/Variables и рабочий Dev, без скрытых ручных шагов на каждый деплой.
- Prod, Kafka, ETL и полная бизнес-функциональность не добавлены в этот этап.

В финальном отчёте дай ссылки на четыре GitHub-репозитория, локальные пути, ветки и SHA, результаты сборок/Actions, версию BMAD и точные команды начала работы. Укажи созданные имена Secrets/Variables и их scope без секретных значений, адрес Dev, фактические результаты health/HTTP и деплоев. Перечисли реальные блокеры, если они остались. Не утверждай, что Dev готов, если деплой не выполнялся или не прошёл проверку.
