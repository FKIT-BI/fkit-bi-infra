# Онбординг: подключение машины за несколько минут

## 1. Проблема

Сейчас в админке три разных входа в одну задачу: чек-лист «Настройка», вкладки CRUD («Предприятия», «Линии и машины», «Смены», «Причины потерь») и «Мастер настройки» (`pages/admin/EquipmentSetup.tsx`). Пользователю непонятно, с чего начинать и в каком порядке идти.

Что именно мешает (по коду `EquipmentSetup.tsx`, `MachineDrawer.tsx`):

| # | Что видит пользователь | Почему это плохо |
|---|---|---|
| 1 | «Мастер» — одна длинная страница из 7 независимых форм, у каждой своя кнопка сохранения | Нет последовательности: непонятно, что уже создано и что дальше |
| 2 | Поля «Код» нужно вводить вручную в формате `[A-Z][A-Z0-9_]` | Пользователь не знает, что такое код, зачем он нужен и чем отличается от названия |
| 3 | Списки с сырыми enum: `MOTOR`, `TEMPERATURE`, `DOUBLE`, `GAUGE`, `IDLE`, `DISABLED` | Непонятные английские слова без объяснения |
| 4 | Поле «Последовательность» (`signalKind`) и «Семантика» (`semanticCode`) | Термины из спецификации, а не из языка пользователя |
| 5 | Правила состояния вводятся как JSON с UUID сигналов | Без программиста не настроить |
| 6 | Длительности в миллисекундах («Offline после, мс» = 60000) | Неудобно, легко ошибиться на порядок |
| 7 | Ошибки полей показываются как `<code>path</code> — текст` | Технический путь вместо подписи поля |
| 8 | Смены не входят в мастер, хотя без них не считаются периоды | Пользователь узнаёт об этом только из чек-листа |
| 9 | Статус машины выводится как `DISABLED` / `ACTIVE` | Непонятно, что машина «ещё не в мониторинге» |

Попутно найденные дефекты старого мастера: при `semanticCode=CUSTOM` подставляется жёстко `customSemanticCode: 'CUSTOM_VALUE'`; каждый сигнал создаётся с `featured: true` и `staleAfterMs: 60000` без ведома пользователя.

## 2. Цель и критерии успеха

**Цель:** новый пользователь без знания модели данных подключает первую машину (предприятие → смены → линия → машина → сигналы → правила → активация) за один последовательный проход.

Критерии:

- Типовой путь — не более ~12 обязательных действий/полей; первая машина подключается ≤ 5 минут.
- На экране нет ни одного сырого кода перечисления: везде русская подпись, при наведении — пояснение.
- Пользователь нигде не обязан вводить код вручную и не видит JSON (JSON остаётся только в режиме «Для экспертов»).
- Каждое поле имеет короткое пояснение «что это и на что влияет».
- Длительности вводятся в секундах/минутах.

Вне рамок: изменения backend API, пакетный endpoint создания, справочник типов машин на сервере.

## 3. Ментальная модель для пользователя

Показываем в справке и в шапке мастера одной схемой с примером:

```text
Предприятие   «Завод упаковки»          — площадка: часовой пояс и смены
 └ Линия      «Линия экструзии 1»       — группа машин на схеме и в отчётах
    └ Машина  «Экструдер Э-1»           — то, по чему считаются работа, простои и OEE
       ├ Узел (компонент) «Шнек»        — необязательно: часть машины, где стоит датчик
       │  └ Сигнал «Температура зоны 1» — значение, которое машина передаёт
       └ Сигнал «Машина в работе»        — сигнал может относиться ко всей машине
Правила состояния: «если "Машина в работе" = да дольше 10 с → Работа»
```

Ключевая мысль, которую объясняем: **сигналы — это то, что машина сообщает; правила — как по сигналам понять, работает ли машина; состояние — итог, из которого считаются простои и показатели.**

## 4. Пошаговый мастер «Подключение машины»

### 4.1. Общая механика

- Mantine `Stepper`, 7 шагов, слева — номер и название шага, справа — панель «Что это?» с объяснением текущего шага (сворачивается на узких экранах).
- **Каждый шаг сохраняется на сервере сразу**, по кнопке «Сохранить и далее». Так ошибка видна на том шаге, где она возникла: конфликт кода, неверная пара норма/единица, недопустимое сочетание типа и характера сигнала. Пользователь исправляет её, пока помнит контекст, а не разбирает в конце список проблем со всех шагов.
- Порядок проверок на шаге: клиентская валидация (зеркало правил backend: формат кода, пара норма/единица, `staleAfterMs ≥ expectedIntervalMs`, `tolerance` для DOUBLE `EQ/NE`, типы literal в правилах) → запрос(ы) шага → при ошибке форма остаётся на шаге, ошибки сервера (`fieldErrors[].path`) показываются у соответствующих полей с русскими подписями; путь как `<Code>` не показываем.
- При `409 *_CODE_CONFLICT` для автоматически сгенерированного кода фронт сам добавляет суффикс (`_2`, `_3`) и повторяет запрос один раз; если код ввёл пользователь, показываем ошибку у поля кода.
- **Машина до шага 7 остаётся отключённой** (`DISABLED`, в UI «Не подключена»): созданные объекты не попадают в мониторинг и расчёты, пока настройка не завершена. Предприятие, смены, причины и линия создаются активными, но без подключённых машин они пусты в мониторинге. Поэтому сохранять по шагам безопасно.
- **Возврат назад = редактирование.** Если объект шага уже создан, «Сохранить и далее» вызывает `PUT` (обновление), а не повторное создание. Форма показывает отметку «Сохранено ✓». После создания нельзя менять код (неизменяем в API); до первых данных можно менять формат, характер и семантику сигнала.
- **Удаления в API нет.** Убранный на шаге 5 сигнал или узел, который уже сохранён, переводится в `DISABLED` с подсказкой «Сигнал отключён и не будет использоваться». Отключённые скрываются из мастера, но видны в справочниках.
- **Прогресс мастера** (id созданного предприятия, линии, машины, сигналов и номер текущего шага) хранится в `sessionStorage` (как сейчас `DRAFT_KEY`) и переживает истечение JWT. Несохранённые поля текущего шага тоже сохраняются в черновик.
- **Продолжение незавершённой настройки.** Если пользователь ушёл из мастера, машина остаётся «Не подключена». Чек-лист «Настройка» и список машин показывают у неё кнопку «Продолжить настройку»: мастер открывается на первом незавершённом шаге, который определяется по серверным данным (есть ли сигналы, есть ли правила, `activation-readiness`), а не только по черновику. Это работает и в другом браузере.
- Шаги, уже выполненные ранее, сворачиваются в одну строку: если у предприятия есть смены, шаг «Смены» показывает «3 смены настроены ✓, изменить».

| Шаг | Название в UI | Обязательные поля в типовом пути | Что сохраняется по «Сохранить и далее» |
|---|---|---|---|
| 1 | Предприятие | выбрать существующее **или** название + часовой пояс | `POST /enterprises` (если новое) или `PUT` при правке |
| 2 | Смены и причины потерь | выбрать шаблон смен (1 клик); причины — галочка «типовой справочник» | смены по одной `POST .../shifts`, затем причины `POST .../loss-reasons` |
| 3 | Линия | выбрать существующую **или** название | `POST .../lines` (если новая) |
| 4 | Машина | название; норма выпуска — по желанию | `POST .../machines` с `lineId`, статус `DISABLED` |
| 5 | Сигналы | выбрать 1+ шаблонов сигналов, при желании переименовать | сначала новые узлы (`POST .../components`), затем сигналы (`POST .../telemetry-signals`) |
| 6 | Как определять состояние | ответить на 1–2 вопроса (или принять предложенное) | `POST .../state-configuration/validate`, при успехе `PUT .../state-configuration` |
| 7 | Проверка и запуск | кнопка «Подключить машину» | `GET .../activation-readiness`, затем `PUT .../status ACTIVE` |

Шаг 2 создаёт несколько объектов. Если один запрос упал, уже созданные смены и причины помечаются ✓, упавший — красным с текстом ошибки. «Повторить» отправляет только несохранённые. Так же работает шаг 5 для набора сигналов.

(Шаг 7 — экран итога, в `Stepper` это `Stepper.Completed`/финальный шаг.)

### 4.2. Шаг 1. Предприятие

- Если предприятия есть — список карточек «Выбрать»; ниже «+ Новое предприятие».
- Новое: «Название» (обязательно), «Часовой пояс» (список с русскими подписями: «Москва (UTC+3)», «Калининград (UTC+2)», «Екатеринбург (UTC+5)», «Новосибирск (UTC+7)», «Владивосток (UTC+10)»; по умолчанию — часовой пояс браузера, если он есть в списке, иначе Москва).
- Код скрыт в «Дополнительно» (см. раздел 6).
- Пояснение: «Часовой пояс нужен, чтобы смены и сутки считались по местному времени завода».

### 4.3. Шаг 2. Смены и причины потерь

- Шаблоны смен одной кнопкой (карточки):
  - «Две смены по 12 ч» — День 08:00–20:00, Ночь 20:00–08:00;
  - «Три смены по 8 ч» — 1-я 07:00–15:00, 2-я 15:00–23:00, 3-я 23:00–07:00;
  - «Одна смена» — 08:00–17:00;
  - «Настроить вручную» — таблица «Название / Начало / Конец».
- `validFrom` = сегодня, `sortOrder` по порядку, коды — автоматически (`DAY`, `NIGHT`, `SHIFT_1`…).
- Пояснение: «По сменам считаются отчёты, хронометраж и сравнение "смена к смене". Смена может переходить через полночь».
- Причины потерь: галочка «Добавить типовой справочник причин» (по умолчанию включена) — 8–10 причин по категориям «Оборудование», «Материалы», «Персонал», «Переналадка»… Пояснение: «Из этого списка оператор выбирает, почему машина стояла. Можно дополнить позже».
- Если у предприятия смены уже есть — шаг свёрнут с отметкой ✓.

### 4.4. Шаг 3. Линия

- Выбрать существующую линию предприятия или «+ Новая линия» (только «Название»).
- Вариант «Без линии» доступен, но не по умолчанию, с подсказкой «машина не попадёт в группировку по линиям; назначить можно позже».
- Пояснение: «Линия — это группа машин, работающих вместе. На обзоре предприятия машины показываются по линиям».

### 4.5. Шаг 4. Машина

Основное:
- «Название» (обязательно), пример в placeholder: «Экструдер Э-1».
- «Тип машины» — свободный ввод с подсказками (`Autocomplete`): Экструдер, Пресс, Термопластавтомат, Упаковочная машина, Станок ЧПУ, Конвейер, Миксер… Тип используется для предложения набора сигналов на шаге 5 (только на фронте; backend хранит `machineType` как строку).
- «Норма выпуска» — одно составное поле «[ 120 ] [шт/ч ▾]»; пояснение: «Сколько продукции машина выпускает в час при нормальной работе. Нужно для расчёта производительности и OEE. Можно пропустить». Пара проверяется `rateUnitError`.

«Паспорт (необязательно)» — свёрнуто: инвентарный номер, производитель, модель, год ввода, код.

### 4.6. Шаг 5. Сигналы — «Что машина передаёт?»

Главная идея: **пользователь выбирает шаблоны, а не заполняет поля** `valueType/signalKind/semanticCode`.

- Сетка карточек-шаблонов (галочка на карточке = добавить сигнал). Каждый шаблон заполняет тип значения, характер, «что измеряет», единицу и пороги свежести:

| Шаблон в UI | Подпись на карточке | `semanticCode` | `valueType` / `signalKind` | Единица по умолчанию |
|---|---|---|---|---|
| Машина в работе | «Да/нет: машина сейчас работает» | `OPERATING_FLAG` | BOOLEAN / STATE | — |
| Авария | «Да/нет: есть авария» | `ALARM_FLAG` | BOOLEAN / STATE | — |
| Готовность | «Да/нет: машина готова к пуску» | `READY_FLAG` | BOOLEAN / STATE | — |
| Скорость | «Скорость линии или подачи» | `LINEAR_SPEED` | DOUBLE / GAUGE | м/мин |
| Обороты | «Частота вращения вала/шпинделя» | `ROTATIONAL_SPEED` | DOUBLE / GAUGE | об/мин |
| Температура | «Температура узла или среды» | `TEMPERATURE` | DOUBLE / GAUGE | °C |
| Давление | «Давление в системе» | `PRESSURE` | DOUBLE / GAUGE | бар |
| Нагрузка | «Загрузка машины, %» | `LOAD_PERCENT` | DOUBLE / GAUGE | % |
| Ток двигателя | «Потребляемый ток» | `CURRENT` | DOUBLE / GAUGE | А |
| Счётчик продукции | «Сколько изделий выпущено (растёт)» | `PRODUCTION_COUNT` | LONG / COUNTER | шт |
| Счётчик брака | «Сколько изделий забраковано» | `SCRAP_COUNT` | LONG / COUNTER | шт |
| Режим работы | «Авто / ручной / наладка (код режима)» | `MACHINE_MODE` | LONG / STATE | — |
| Свой сигнал | «Любая другая величина» | выбор из полного списка | выбор | выбор |

  Единица подставляется, только если она есть в справочнике `GET /reference/measurement-units` (поиск по `quantityCode`/`code`); иначе поле единицы остаётся пустым и подсвечено.

- По «Типу машины» шаг предлагает набор: «Для экструдера обычно передают: Машина в работе, Авария, Скорость, Температура, Счётчик продукции — добавить все?».
- Выбранные сигналы — список строк: «Название» (предзаполнено из шаблона, можно поменять), «Где установлен» (необязательно: узел машины), значок ★ «Показывать на карточке» (по умолчанию ★ у первых 3 сигналов), «⋯ Дополнительно» (диапазон min/max, «Значение приходит раз в», «Считать устаревшим через», код).
- **Узел (компонент)** создаётся прямо здесь: в поле «Где установлен» — «+ Новый узел» → название + вид из сгруппированного списка (см. словарь). Отдельного шага для компонентов нет: пояснение «Узел — необязательная часть машины (двигатель, насос, шнек). Нужен, чтобы сигналы группировались по узлам. Если не уверены — оставьте "Вся машина"».
- `staleAfterMs` всегда задаётся (обязателен для сигналов в правилах): по умолчанию 60 с, показывается как «Считать устаревшим через: 1 мин».
- Свой сигнал: три понятных вопроса вместо трёх enum:
  1. «Что измеряет?» — список семантик с русскими названиями и описанием (или «Другое» + своё название, из которого автоматически строится `customSemanticCode`);
  2. «Какое значение приходит?» — «Дробное число / Целое число / Да или нет / Текст»;
  3. «Как ведёт себя значение?» — «Текущее измерение / Накопительный счётчик / Состояние или код» (недопустимые сочетания скрыты по таблице совместимости).

### 4.7. Шаг 6. Как определять состояние

Вместо JSON — **вопросы**, ответы на которые превращаются в правила (`StateRuleInput`). Начальное заполнение — `suggestRules()` по выбранным сигналам.

Экран:

1. «Когда считать, что машина **в работе**?» — радио:
   - «Когда "Машина в работе" = да» (если есть флаг);
   - «Когда "Скорость" больше [ 5 ] м/мин» (если есть скорость/нагрузка/обороты);
   - «Задать своё условие».
2. «Когда считать, что машина **в аварии**?» — чекбоксы:
   - «Когда "Авария" = да»;
   - «Когда "Температура" не ниже [ 90 ] °C» (если есть температура);
   - «Не определять аварию автоматически».
3. «Во всех остальных случаях машина…» — `defaultState`, по умолчанию «Простой», с пояснением: «Если ни одно правило не сработало, машина считается в простое. Это неплановая потеря времени».
4. «Если данные не приходят [ 1 ] мин — показывать "Нет данных"» (`offlineAfterMs`).
5. Задержки — в каждой строке условия: «…держится не меньше [ 10 ] с» (`activationDelayMs`); «Выход из состояния после [ 30 ] с» скрыто в «Дополнительно» (`releaseDelayMs`).

Приоритет не показываем: он выставляется автоматически по порядку «Авария (100) > Работа (50)»; в расширенном режиме — перетаскивание строк «выше = важнее».

**Расширенный конструктор** («Настроить правила подробно»): таблица правил «Название / Если / Тогда состояние / Задержка», условие собирается строками «[сигнал ▾] [оператор ▾] [значение]» и группой «все условия / любое из условий». Операторы ограничены по типу сигнала (таблица совместимости из `condition-ast.md`), для DOUBLE `равно` автоматически добавляет поле «допуск». JSON-редактор — только вкладка «Для экспертов».

Под формой — живая подсказка-превью: «Работа — если "Машина в работе" = да дольше 10 с. Авария — если "Авария" = да дольше 5 с. Иначе — Простой. Нет данных > 1 мин — "Нет данных"».

К этому шагу машина и сигналы уже сохранены, поэтому правила проверяются настоящим серверным `validate` с реальными id сигналов. Кнопка «Проверить» доступна в любой момент. «Сохранить и далее» сначала вызывает `validate`, затем `PUT`. Ошибки (`errors[].path`) привязываются к конкретной строке правила и полю; предупреждения показываются, но не блокируют переход.

### 4.8. Шаг 7. Проверка и запуск

- Сводка всех шагов человеческим языком с кнопками «Изменить».
- Всё уже сохранено на шагах 1–6. Экран сразу запрашивает `activation-readiness` и показывает результат: «Всё готово к подключению» или список замечаний (`message` с сервера) со ссылкой «Исправить» на нужный шаг.
- Предупреждения (`warnings`) не блокируют подключение. Ошибки (`errors`) блокируют кнопку «Подключить машину».
- «Подключить машину» = `PUT .../status ACTIVE`. При ошибке форма остаётся на шаге, машина остаётся «Не подключена», настройка не теряется.
- После успеха: «Машина "Экструдер Э-1" подключена и в мониторинге» + три кнопки:
  - «Сгенерировать тестовые данные» (существующий `QuickGenerateModal`);
  - «Подключить ещё машину на эту линию» — мастер стартует с шага 4, предприятие/смены/линия уже выбраны, на шаге 5 предложение «Скопировать набор сигналов и правил с "Экструдер Э-1"»;
  - «Открыть мониторинг».

## 5. Место в админке

- Вкладка «Мастер настройки» заменяется новым мастером; вкладка переименовывается в «Подключить машину» и стоит первой.
- Чек-лист «Настройка» остаётся как обзор готовности, но его главная кнопка — «Подключить машину», а пункты ведут в соответствующий шаг мастера.
- При пустом списке предприятий `/admin` открывается сразу на мастере (empty state «Начнём с подключения первой машины»).
- Вкладки CRUD остаются для правки существующего, переименовываются в группу «Справочники» и используют те же словари и подсказки.
- Старый `EquipmentSetup.tsx` удаляется после переноса.

## 6. Код и название

Сейчас пользователь должен сам придумать код. Новое правило:

- **Название** — то, что видят люди; можно менять в любой момент.
- **Код** — технический идентификатор латиницей для интеграций, генератора и выгрузок; уникален внутри родителя и **не меняется после создания**.
- Код генерируется автоматически из названия: транслитерация (ГОСТ 7.79-2000, схема Б, упрощённо) → верхний регистр → всё, кроме `A–Z0–9`, в `_` → схлопнуть `_` → если начинается не с буквы, префикс по типу объекта (`M_`, `L_`, `S_`…) → обрезка до 64 → уникализация суффиксом по уже загруженным спискам. «Экструдер Э-1» → `EKSTRUDER_E_1`.
- Поле кода спрятано в «Дополнительно», рядом пояснение: «Заполняется автоматически. Меняйте, только если код нужен для интеграции. После создания изменить нельзя».

## 7. Справка в интерфейсе

Три уровня, все тексты — в одном модуле словарей (раздел 8):

1. **Подпись + подзаголовок поля** (`description` у Mantine-инпута) — 1 строка «на что влияет».
2. **ⓘ у сложных полей** — tooltip/popover 1–3 предложения и пример.
3. **Панель «Что это?»** справа в мастере и кнопка «Справка» в шапке админки — drawer с глоссарием (раздел 8.1) и схемой иерархии (раздел 3).

Во всех `Select` с перечислениями — `renderOption` с двумя строками: русское название и серое описание. Поиск по списку работает и по русскому названию, и по коду.

## 8. Словари (переводы и пояснения)

Реализация: `fkit-bi-web/src/shared/i18n/dictionaries.ts` — объекты типа `Record<EnumType, { label: string; hint?: string }>` по сгенерированным типам API, чтобы TypeScript ловил непереведённое значение. Хелпер `enumLabel(dict, code)` с фоллбэком на код (для открытых списков вроде `semanticCode`). `ru.state` переиспользуется, а не дублируется.

### 8.1. Глоссарий

| Термин | Пояснение для пользователя |

| Причина потерь | Почему машина стояла: поломка, нет материала, переналадка… Выбирается оператором при разборе простоя. |
| Линия | Группа машин, работающих вместе. Используется для группировки на обзоре и в отчётах. |
| Машина | Единица оборудования, по которой считаются работа, простои, OEE. |
| Узел (компонент) | Необязательная часть машины: двигатель, насос, шнек. Нужен для группировки сигналов. Узлы могут быть вложенными. |
| Сигнал | Значение, которое машина передаёт: температура, скорость, «в работе да/нет», счётчик изделий. |
| Что измеряет (семантика) | Физический смысл сигнала. По нему система понимает, что это за величина, и предлагает правила. |
| Формат значения (тип значения) | Как записано значение: дробное число, целое, да/нет, текст. |
| Характер сигнала (вид сигнала) | Как ведёт себя значение во времени: текущее измерение, накопительный счётчик или состояние/код. |
| Единица измерения | °C, бар, шт, м/мин… Берётся из справочника. |
| Главный сигнал (★) | Показывается на карточке машины в мониторинге. |
| Значение приходит раз в | Как часто ожидаются новые данные. Нужно для контроля качества данных. |
| Считать устаревшим через | Если новое значение не пришло за это время, старое перестаёт учитываться в правилах. |
| Допустимый диапазон | Физически возможные min и max. Значения вне диапазона сохраняются, но помечаются как сомнительные. |
| Норма выпуска | Сколько продукции машина выпускает в час при нормальной работе. Нужна для производительности и OEE. |
| Состояние машины | Итог по правилам: Работа, Простой, Авария, Переналадка, Плановая остановка, Нет данных. |
| Правило состояния | «Если условие по сигналам выполняется дольше N секунд — машина в состоянии X». |
| Важность (приоритет) | Если сработало несколько правил, побеждает более важное (выше в списке). |
| Задержка включения | Сколько условие должно держаться, чтобы состояние сменилось. Защищает от кратких всплесков. |
| Задержка выхода | Сколько должно пройти после пропадания условия, чтобы выйти из состояния. |
| Состояние по умолчанию | Если ни одно правило не сработало. Обычно «Простой». |
| Нет данных через | Через сколько без новых данных машина считается «Нет данных» (нет связи). |
| Код | Технический идентификатор латиницей. Создаётся автоматически, после создания не меняется. |
| Название | Как объект видят люди. Можно менять. |
| Активна / Отключена | Активные объекты участвуют в мониторинге и расчётах; отключённые сохраняются, но не используются. Удаления нет. |

## 10. Acceptance criteria

- Given пустой стенд без предприятий, when администратор открывает `/admin`, then сразу открывается мастер и за один проход создаются предприятие, смены, типовые причины, линия, машина, сигналы, правила, и машина становится «В мониторинге».
- Given шаг мастера с ошибкой сервера (например, конфликт кода или неверная пара норма/единица), when пользователь нажимает «Сохранить и далее», then мастер остаётся на этом шаге и показывает ошибку у соответствующего поля на русском.
- Given уже сохранённый шаг, when пользователь возвращается и меняет данные, then объект обновляется (`PUT`), дубль не создаётся; убранный сохранённый сигнал переводится в «Отключено».
- Given машина сохранена на шагах 4–6, но не подключена, when пользователь закрывает мастер, then машина остаётся «Не подключена», не попадает в мониторинг, а «Продолжить настройку» открывает первый незавершённый шаг (определяется по серверным данным).
- Given истёк JWT в середине шага, when пользователь входит снова, then несохранённые поля текущего шага восстанавливаются из черновика.
- Given ошибка на шаге создания N, when пользователь нажимает «Повторить», then уже созданные объекты не дублируются, процесс продолжается с шага N.
- Given любая форма админки, when пользователь открывает список «вид узла», «что измеряет», «формат», «характер», «состояние», then видит русские названия с пояснениями; ни один экран не показывает сырые enum (проверяется тестом по DOM на шаблон `\b[A-Z]{2,}(_[A-Z]+)+\b` вне полей «код»).
- Given название «Экструдер Э-1», when создаётся машина, then код `EKSTRUDER_E_1` (или с суффиксом при конфликте) формируется без ввода пользователя.
- Given выбраны шаблоны «Машина в работе» и «Авария», when открыт шаг 6, then предложены правила «Работа: флаг = да» и «Авария: флаг = да», состояние по умолчанию «Простой», и сохранение проходит `validate` без правки JSON.
- Given TypeScript-типы API, when в enum появляется новое значение, then сборка падает, пока не добавлен перевод.

### WEB-006 и WEB-007 — review (2026-10-15)

Ветка `feature/onboarding-dictionaries-autocodes` в `fkit-bi-web`, детали — `fkit-bi-web/docs/tasks/WEB-006-007-dictionaries-autocodes.md`.

- Словари: `src/shared/i18n/dictionaries.ts` (состояния, статусы, формат и характер сигнала, «что измеряет», виды узлов с группами, операторы, свежесть, качество, источники, часовые пояса, подписи полей для `fieldErrors[].path`, глоссарий, пояснения к полям).
- Общие компоненты: `src/shared/ui/form.tsx` — `EnumSelect` (подпись + пояснение, поиск по-русски и по коду, группы), `HintLabel` (ⓘ), `DurationInput` (секунды/минуты/часы ↔ мс), `useAutoCode` + `CodeField`, `HelpDrawer`.
- Автокод: `src/shared/lib/code.ts` — `makeCode(name, prefix, taken)`. Подключён в формах предприятия, смены, причины, линии, машины, узла, сигнала, параметров машины, сценария генерации и в старом мастере.

- `FormModal` выводит ошибки сервера, которые не показаны у полей, с русскими подписями полей вместо `path`.

Отклонения от спецификации:
- `DISABLED` у машины всегда подписывается «Не подключена»: API не сообщает, активировалась ли машина раньше, поэтому вариант «Отключена» (8.3) не различается.
- Подбор единицы измерения по семантике отложен в WEB-008 (шаблоны сигналов).
- Тест на отсутствие сырых enum проверяет форму и таблицу сигналов и словари, а не каждый экран приложения.
- В мок-данных у части сигналов семантики вне каталога (`SPEED`, `LOAD`, `OUTPUT_COUNTER`) — они показываются кодом (фоллбэк `enumLabel`).

### WEB-008…011 — review (2026-10-15)

Ветка `feature/onboarding-wizard` в `fkit-bi-web`, детали — `fkit-bi-web/docs/tasks/WEB-008-011-onboarding-wizard.md`.

- WEB-008: каталог шаблонов сигналов и наборы по типу машины (`src/features/onboarding/templates.ts`); единица подбирается из справочника по `quantityCode`. Справочник единиц переведён на фронте: backend отдаёт названия и символы по-английски.

- Смены и причины мастер создаёт, только если их у предприятия ещё нет; изменение существующих — через вкладки справочников.
