# Epic 6 Context: Generator configuration and run control

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Дать пользователю возможность настраивать повторно используемые сценарии генерации исходных показаний и запускать их в реальном времени, для исторического периода или в заданный момент в будущем. Запуски должны быть управляемыми, устойчивыми к повторам и сбоям, воспроизводимыми по сохранённому снимку конфигурации и не создавать конкурирующую модель оборудования или готовые состояния станков.

## Stories

- Story 6.1: Scenario API and storage
- Story 6.2: Immutable run snapshot
- Story 6.3: Realtime execution
- Story 6.4: Historical and scheduled execution
- Story 6.5: Generator acceptance

## Requirements & Constraints

- Сценарий принадлежит одному предприятию и может включать несколько его станков. Используются существующие Enterprise, ProductionLine, Machine, Component и TelemetrySignal; Generator не предоставляет CRUD оборудования. Сценарий имеет стабильный код и статус `ACTIVE|DISABLED`; неполный сценарий можно сохранить выключенным, но включение и запуск требуют полной проверки принадлежности, статусов, назначения станков на линии, сигналов и совместимости моделей поведения.
- Сценарий задаёт упорядоченные фазы и `ONCE|LOOP`. Поведение сигнала задаётся базовой конфигурацией и одноуровневыми фазовыми переопределениями `REPLACE|DISABLE`; частичное объединение параметров не используется. `expectedState` — только подсказка для диагностики: Generator публикует raw-показания, а состояние машины рассчитывает Analytics.
- Каждый запуск сохраняет неизменяемый снимок сценария и нужных данных оборудования/сигналов вместе с deterministic seed. Последующие изменения или отключение сущностей не меняют активный запуск. Отдельные версии сценариев и оборудования не вводятся.
- Run и его прогресс долговечны в PostgreSQL. Запуск асинхронный; поддерживаются статусы, остановка и ограниченный retry. Повтор создания с тем же `Idempotency-Key` и телом возвращает исходный Run; иной запрос с тем же ключом отклоняется. Retry допускается только для retryable `FAILED` и сохраняет ID, снимок и seed.
- Realtime пропускает опоздавшие ticks без catch-up burst; ограничиваются буфер, запись и retry. Historical использует UTC-диапазон в пределах активного 90-дневного raw window, пятиминутные checkpoints, детерминированные batch IDs и throttling. При retry незавершённые batches безопасно повторяются; checkpoint фиксируется только после подтверждения всех batches chunk. На минимальном стенде допускается один historical Run.
- Future-запуск хранит точный UTC instant. До наступления времени telemetry не создаётся; перед стартом повторно проверяется актуальная готовность оборудования. Опоздание более 30 секунд завершает Run ошибкой `SCHEDULE_MISSED`.
- Остановка текущего Run не обрывает транзакцию batch: текущая запись завершается или откатывается, новые пакеты не формируются, flush ограничен timeout. Внешний HTTP API не принимает raw telemetry и не ждёт завершения Analytics-пересчёта; `COMPLETED` означает завершение генерации, не готовность аналитики.
- Приём данных использует внутренний `TelemetrySink` и append-only batch-контракт Analytics. Measurement содержит существующий signal ID, event time, одно типизированное значение, качество и flags; официальные состояния, KPI и интервалы не передаются. Пакет ограничен 1000 строками, batch retry идемпотентен.
- Приёмка покрывает все 12 публичных операций, детерминированные golden data, гонки резервирования и критерии AC-8/9.

## Technical Decisions

- Generator — отдельное Spring-приложение и владелец только схемы `generator` и записи raw через согласованный append-контракт. Общая PostgreSQL — интеграционная граница; миграциями всех схем владеет Analytics. Generator запускается после готовности Analytics и проверяет поддерживаемый `equipment.schema_release`.
- Run creation атомарно читает текущую конфигурацию и записывает самостоятельный снимок с развёрнутой effective behavior matrix и seed. Для запланированного запуска readiness повторно проверяется в момент старта, но сохранённый снимок не перестраивается.
- Резервирование станков долговечно и координируется через PostgreSQL: realtime не делит станок с другим активным realtime, будущие интервалы резервирования не пересекаются; многомашинный запуск резервируется атомарно. Historical использует отдельную общую квоту.
- Historical coverage для одной машины не должна пересекаться с уже подтверждённым диапазоном. Batch IDs детерминированы от Run и позиции в chunk; это позволяет восстановить выполнение без повторного raw-эффекта. Generator не создаёт raw partitions и не выполняет DDL.
- Публичный versioned API покрывает шесть операций сценариев и шесть операций запусков; base path сервиса `/api/v1`, внешний proxy prefix — `/api/generator/`. Запрос создания Run возвращает `202`; общий JWT Bearer и стабильные коды ошибок согласованы с API Analytics.
- Прогресс bounded run определяется event-time coverage; для unbounded realtime и ожидающего scheduled run процент равен null. Active detail опрашивается примерно каждые 2 секунды, списки — каждые 10 секунд; потоки событий в MVP не предусмотрены.

## UX & Interaction Patterns

- Интерфейс использует каталог оборудования Analytics; сигналы загружаются лениво для выбранных станков. Страница Generator загружает дерево оборудования, сценарии и активные запуски тремя ограниченными запросами.
- Редактор сценария визуально различает унаследованное базовое поведение, `REPLACE` и `DISABLE`. Ошибки проверки привязываются к полям по путям из ответа; активация выполняется отдельной командой.
- Диалог запуска показывает поля выбранного режима. Создание повторяется с прежним ключом идемпотентности только при сетевом повторе; статус запуска отслеживается polling, а остановка идемпотентна. Retry предлагается только для retryable failure.
- Переход к аналитике использует фактические `eventFrom` и `generatedThrough`; готовность данных определяется метаданными Analytics (`dataThrough`, `stale`, `recalculating`), а не статусом Generator.

## Cross-Story Dependencies

- Epic 6 зависит от стабильного контракта telemetry и готовности оборудования из Epic 3; Generator использует уже существующие equipment/signal записи и append-only writer contract Analytics.
- Разработку можно вести параллельно с Epic 4 после стабилизации этих контрактов, но интеграционная приёмка требует Epic 3. Итоговая релизная проверка Epic 7 зависит от завершения Epic 6.
