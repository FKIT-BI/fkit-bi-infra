topic: Транзакционные границы и идемпотентность Java-сервисов FKIT BI
goal: Зафиксировать атомарность команд, публикаций и безопасное восстановление фоновой аналитики на PostgreSQL для MVP
updated: 2026-10-10T18:12
---

- (direction by user) Пользователь согласовал следующий блок аналитики по транзакциям и идемпотентности и выбрал единый persistence-подход Spring JDBC без JPA как основного MVP пути.
- (decision by user) Java application/service layer задаёт транзакционные границы декларативно через Spring @Transactional; DAO/JDBC adapters участвуют в той же PostgreSQL transaction.
- (decision by user) Spring JDBC JdbcTemplate/NamedParameterJdbcTemplate является единым основным persistence API MVP; доменные/application модели не связываются с JDBC типами.
- (decision by user) Использовать параметризованный SQL, JDBC batch для ingestion/массовых операций и SQL read projections; PostgreSQL COPY вводить только если benchmark докажет необходимость.
- (decision by user) Machine configuration изменяется полной атомарной командой; ошибка validation/persistence не оставляет частичной конфигурации.
- (decision by user) Telemetry batch transaction включает header, measurements, durable signal usage и recalculation hints; batch idempotency использует producer identity, batch ID и canonical payload hash.
- (decision by user) Длительный расчёт и staging выполняются вне транзакции активных проекций; validated staged range публикуется одной короткой транзакцией замены и обновления currency/job/checkpoint.
- (decision by user) ManualIncident mutation и durable dirty work записываются одной транзакцией; аналитическая effective projection пересчитывается асинхронно и остаётся старой committed версией до успешной публикации.
- (decision by user) Фоновые шаги выполняются at-least-once и делают идемпотентный replace/upsert, не additive replay; publication и успешное завершение durable work фиксируются атомарно.
- (constraint by user) Чтение API обслуживается committed projections через PostgreSQL MVCC; оно не ждёт долгого расчёта и не читает staging.
- (note by analyst) Внешние эффекты (HTTP, метрики, логи) не откатываются транзакцией PostgreSQL и не должны выполняться как будто они атомарны с commit.
- (capability by analyst) CAP-1: Каждый durable command фиксируется целиком либо не оставляет частичных изменений; успех проверяется конкурентным отказом и rollback case для полного комплекта связанных rows.
- (capability by analyst) CAP-2: Analytics может пересчитать и опубликовать диапазон без блокировки чтения готовой аналитики; успех — до commit видна старая полная проекция, после commit новая полная проекция.
- (capability by analyst) CAP-3: Workers безопасно повторяют незавершённые шаги после сбоя; успех — повтор не удваивает ни один bucket/duration и завершённый publication не выполняется как частично успешный.
- (decision by analyst) При обновлении StateRule, ManualIncident или ином изменении, требующем analytics replay, изменение доменных данных и durable dirty work фиксируются в одной transaction; replay асинхронный.
- (decision by analyst) В каждой публикационной transaction вместе коммитятся replace затронутых проекций, currency/current fields, успешный статус связанного job/work и checkpoint; сбой откатывает весь publication.
- (decision by analyst) Durable staging заполняется и проверяется вне publication transaction; incomplete stage после crash пересоздаётся из raw и durable work, bounded cleanup не влияет на активные reads.
- (decision by analyst) Service methods form transaction boundaries across repositories sharing the application DataSource and transaction manager; persistence adapters return mapped DTO/records rather than exposing JDBC objects to domain/application callers.
- (constraint by analyst) Долгий replay, ожидание ресурсов, сеть и построение staged результата запрещены внутри transaction, удерживающей locks проекций; внешние side effects не считаются откатываемыми PostgreSQL.
- (question by analyst) Ретраи POST create ManualIncident при неопределённом сетевом ответе могут создать два разных инцидента; необходимость Idempotency-Key для таких команд отдельно решить при финальной проверке API и надежности.
- (decision by analyst) В рамках поручения ускорить проектирование зафиксировано обязательное `Idempotency-Key` для ManualIncident create: повтор с тем же ключом и каноническим body возвращает исходный результат, конфликтующий body отклоняется; scope ключа — authenticated user + operation.
- (event by analyst) Coherence validation passed: требование ManualIncident idempotency отражено в SPEC и transaction matrix; API convention синхронизирована. Срок хранения ключей и точная таблица persistence остаются реализационными параметрами общего idempotency adapter.
- (event by analyst) Coherence validation passed: kernel capabilities meet intent/success requirements; JDBC choice, transactional matrix, async publication and retry semantics are consistent across SPEC and companion.
- (event by analyst) Preservation validation passed: accepted service-level rollback, Spring JDBC, batch SQL, durable dirty work, incident async replay, MVCC publication, generator/ingestion idempotency and recovery are captured; unresolved ManualIncident POST key is explicit.
