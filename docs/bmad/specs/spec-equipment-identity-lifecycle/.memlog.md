- (direction) Пользователь подтвердил отдельный компактный spec-пакет для каждого согласованного связного блока требований.
- (decision) Каждая основная конфигурационная сущность имеет внутренний UUID id и отдельный стабильный читаемый технический code.
- (decision) UUID id генерируется backend, используется для SQL-связей и API-адресации и никогда не изменяется.
- (decision) Технический code используется в конфигурации, правилах, генераторе, логах и будущих интеграциях; отображаемое name может изменяться.
- (decision) Коды уникальны в своих областях: Enterprise глобально; Shift и Line внутри Enterprise; Machine внутри Enterprise; Component и TelemetrySignal внутри Machine; LossReason глобально.
- (decision) После создания code не изменяется.
- (decision) Для Machine неизменны id, code и lineId в MVP; inventoryNo допускает исправление как учётный атрибут; name, type, nominalRate, order, status, parameters, components, signals, rules и thresholds редактируемы при сохранении инвариантов.
- (decision) Конфигурационные сущности используют только статусы ACTIVE и DISABLED, устанавливаемые пользователем.
- (decision) Операционное состояние Machine RUN/IDLE/DOWN/PLANNED_STOP/SETUP/OFFLINE вычисляется отдельно из входящей телеметрии и не заменяет конфигурационный статус.
- (decision) Component и Sensor в MVP не имеют отдельного вычисляемого operational state; их поведение отражается в TelemetrySignal и состоянии Machine.
- (decision) Конфигурационные сущности не удаляются физически через пользовательский API; вместо удаления используется DISABLED.
- (decision) Machine в MVP закреплена за ProductionLine и не переносится; перенос оставлен будущим расширением.
- (decision) Component, Sensor и Instrument в MVP закреплены за Machine и не переносятся между машинами.
- (capability) CAP-1: Система однозначно адресует каждую конфигурационную сущность неизменяемым UUID и предоставляет стабильный читаемый code для конфигурации и диагностики.
- (capability) CAP-2: Пользователь может включать и отключать конфигурационные сущности без удаления их истории и связей.
- (capability) CAP-3: Система отделяет административную доступность Machine от её вычисляемого операционного состояния.
- (constraint) MVP не поддерживает физическое удаление использованных конфигурационных сущностей, перенос Machine между Lines и перенос Components между Machines.
- (question) Нужно отдельно утвердить вычисление effectiveStatus по статусам предков и поведение активного generator run при отключении сущности.
