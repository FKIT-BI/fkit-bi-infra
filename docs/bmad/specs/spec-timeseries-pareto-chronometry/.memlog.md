topic: Timeseries, Pareto и Chronometry для demo MVP
updated: 2026-10-08T21:34
---

- (direction) Пользователь согласовал функциональный MVP и потребовал компромисс: простая реализация без чрезмерного урезания аналитических возможностей.
- (capability) CAP-1: Пользователь получает metric timeseries для machine/line/enterprise; успех — каждая точка содержит additive facts и заново рассчитанные ratios с общей freshness metadata.
- (capability) CAP-2: Пользователь получает ограниченный числовой telemetry series; успех — GAUGE и COUNTER возвращают не более 720 информативных points с gaps и quality без тяжёлого raw query.
- (capability) CAP-3: Пользователь видит loss timeseries и Pareto по причинам; успех — IDLE/DOWN/SETUP durations распределены по reason или UNCLASSIFIED, top дополняется OTHER и shares суммируются в 1.
- (capability) CAP-4: Пользователь видит точный chronometry одной машины за occurrence смены; успех — clipped effective intervals не пересекаются, сохраняют manual/calculated source и покрывают готовую часть смены.
- (capability) CAP-5: Все исторические представления единообразно сообщают partial data; успех — requested/actual boundaries, dataThrough, partial и bucket resolution позволяют frontend отличить ноль от отсутствия данных.
- (decision) Общий query period полуоткрытый [from,to), максимум 90 дней в MVP; данные после dataThrough не заявляются готовыми.
- (decision) Исторический envelope содержит requestedFrom/requestedTo/actualFrom/actualTo/dataThrough/partial/resolution и points.
- (decision) AUTO resolution: ≤12h→5m, ≤2d→15m, ≤14d→1h, ≤90d→1d; client может запросить только AUTO/5m/15m/1h/1d.
- (decision) 5m/15m/1h buckets выровнены по UTC; 1d выровнен по локальному календарному дню Enterprise и может иметь 23/25 часов при DST.
- (decision) Shift является фильтром через shiftId; конкретный occurrence задаётся shiftId+shiftDate, а не day/night и не bucket size.
- (decision) Metric point содержит state/coverage durations, output/scrap, stop/failure counts и Availability/Performance/Quality/OEE/dataCoverage, рассчитанные после суммирования минут.
- (decision) Telemetry series поддерживает numeric GAUGE и COUNTER; GAUGE отдаёт min/max/avg/first/last/counts, COUNTER — first/last/delta/resetCount/counts.
- (constraint) Telemetry series ограничен 720 points; server укрупняет resolution до целого числа минут, не интерполирует gaps и не читает большой raw range.
- (decision) Bucket без samples возвращается явной point с sampleCount=0 и null numeric values; unsupported STATE history не маскируется пустым numeric series.
- (decision) MVP loss states для loss denominator: IDLE, DOWN и SETUP; PLANNED_STOP отображается отдельно, OFFLINE остаётся data gap.
- (decision) Loss series содержит idle/down/setup/plannedStop/unclassified durations и массив byReason с nullable reasonId вместо JSON map.
- (decision) Pareto сортируется по duration desc и stable reason code; top default 5 max 20, missing reason=UNCLASSIFIED, остаток=OTHER, no losses=empty list.
- (decision) Pareto share=reasonDuration/totalLoss и cumulativeShare является накопительной суммой отсортированных shares; с OTHER возвращённые shares дают 1.
- (decision) Chronometry MVP принимает machineId+shiftId+shiftDate и возвращает exact effective intervals с state/from/to/duration/calculatedState/source/incidentId/lossReasonId/telemetryQuality.
- (decision) Chronometry intervals clipped по occurrence и dataThrough, отсортированы, не пересекаются и дополняются totals by state; grouped reason intervals не дублируются.
- (decision) No coverage даёт empty points; partial overlap или clip by dataThrough даёт partial=true; covered no-loss bucket имеет zero loss durations, uncovered bucket имеет null values.
- (constraint) Query не ждёт recalculation и читает последнюю committed projection; lag отражается metadata.
- (decision) Для полноценного и быстрого Pareto добавляется machine_loss_bucket_1m с state, nullable lossReasonId и durationMs; он пересчитывается и публикуется вместе с machine metrics.
- (constraint) Новых 5m/15m/1h/1d физических таблиц и отдельного worker pipeline не создаётся; response buckets группируются из минутных projections.
- (decision) Draft API меняется: AUTO/fixed resolution вместо hour/shift/day, object points вместо timestamp-value tuples, UNCLASSIFIED/OTHER Pareto, shiftId+shiftDate chronometry и freshness envelope.
- (event) Пользователь условно согласовал блок после проверки полноты; loss rollup добавлен как необходимый компромисс между функциональностью и простой быстрой реализацией.
- (decision) Внутри actualFrom/actualTo series возвращает каждый response bucket: no event/loss=zero, metric coveredSec=0 даёт null ratios, telemetry no samples даёт sampleCount=0 и null numeric values.
- (decision) Metric и loss series ограничены 1000 points; AUTO укрупняет resolution, а явно запрошенная слишком мелкая resolution отклоняется как RESULT_TOO_LARGE.
- (decision) Loss series и Pareto возвращают top named reasons default 5 max 20, всегда отдельно UNCLASSIFIED при наличии и объединяют остальные named reasons в OTHER.
- (constraint) Chronometry одной смены ограничен 10000 intervals; превышение возвращает CHRONOMETRY_TOO_LARGE без усечения timeline.
- (event) Coherence validation passed: five capabilities have intent and testable success; resolution, limits, gap semantics, loss projection, Pareto and Chronometry are consistent with minute rollups, shifts and metric formulas.
- (event) Preservation validation passed: all accepted views, AUTO thresholds, timezone alignment, telemetry aggregation, UNCLASSIFIED/OTHER, Chronometry fields, partial metadata and draft API changes are represented.
- (event) Spec finalized under functional-MVP direction; three companions exist, response limits and loss-read performance gap are closed, git diff check passed, and reason authoring remains explicitly owned by P14/P15.
- (decision) Chronometry read API requires shiftDate and accepts optional shiftId; with shiftId it returns one occurrence, without it returns all Shift occurrences beginning on that enterprise-local date, ordered by Shift sortOrder then code.
- (constraint) The 10000 interval limit applies to the complete Chronometry response across all returned occurrences; overflow returns CHRONOMETRY_TOO_LARGE without truncation.
