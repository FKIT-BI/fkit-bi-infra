- (direction) Пользователь поручил финализировать новый Analytics API на основе согласованных backend-спецификаций и frontend user flow; старый draft-api остается только источником сценариев.
- (capability) CAP-1: Конфигуратор управляет Enterprise, Shift, LossReason, ProductionLine, Machine, Component, TelemetrySignal и MachineStateConfig раздельными ресурсами; успех — каждый объект создается и изменяется без монолитного Machine DTO и с соблюдением владельца и lifecycle.
- (capability) CAP-2: Конфигуратор проверяет готовность Machine и изменяет ее ACTIVE/DISABLED status; успех — активация атомарно повторяет readiness validation, а ошибки и предупреждения имеют стабильные коды.
- (capability) CAP-3: Оператор получает компактное дерево, обзор предприятия и текущую карточку Machine; успех — статическая конфигурация и динамические projections читаются без N+1 запросов и не смешивают исторический период с current context.
- (capability) CAP-4: Аналитик читает summary и metric timeseries для Machine, Line или Enterprise; успех — backend применяет согласованные формулы, shift filters, previous period и currency metadata без вычисления KPI на frontend.
- (capability) CAP-5: Пользователь читает current и numeric historical telemetry; успех — freshness сигнала отделена от projection currency, а server resolution соблюдает предел 720 points.
- (capability) CAP-6: Аналитик исследует loss timeseries, Pareto, chronometry и effective state intervals; успех — UNCLASSIFIED и OTHER различимы, shift occurrence адресуется через shiftId и shiftDate, а большие результаты не усекаются молча.
- (capability) CAP-7: Оператор создает, исправляет, закрывает и отменяет ManualIncident; успех — overlap и eligibility инварианты проверяются сервером, cancel мягкий, а analytics обновляется асинхронно.
- (capability) CAP-8: Пользователь запускает PERIOD или ALL state recalculation и отслеживает job; успех — HTTP не ждет replay, один active user job на Machine, опубликованные projections заменяются атомарно.
- (capability) CAP-9: Клиент получает единые ошибки, pagination и analytics metadata; успех — generated client различает validation, domain conflict, not found, partial data, stale и recalculating.
- (capability) CAP-10: Новый контракт сохраняет полезные сценарии старого draft и явно заменяет несовместимые DTO; успех — traceability matrix сопоставляет каждую старую operation с новой.
- (decision) Публичный контракт использует OpenAPI 3.1 и base path /api/v1; raw telemetry ingestion и generator control в него не входят.
- (decision) Resource create, update и response DTO разделены; code обязателен на create, предлагается frontend, валидируется backend и после создания неизменяем.
- (decision) Обычный update использует PUT полного набора изменяемых полей; status, parent assignment, line assignment, validation, readiness, close и recalculation оформляются отдельными командами.
- (decision) Конфигурационные списки используют page pagination; intervals, incidents и recalculation journal используют opaque cursor pagination; timeseries используют bounded points без pagination.
- (decision) Resource responses возвращаются напрямую, list responses используют items plus page/cursor metadata, historical analytics responses содержат requested/actual boundaries, dataThrough, calculatedAt, partial и recalculating where applicable.
- (decision) HTTP mapping: 400 malformed query or JSON, 404 absent resource, 409 domain conflict or locked mutation, 422 field or declarative validation, 202 asynchronous recalculation accepted.
- (decision) MVP не публикует security scheme или RBAC; actor names remain analytical personas and UI labels do not grant backend permissions.
- (decision) Machine status changes through PUT /machines/{machineId}/status; ACTIVE repeats readiness checks atomically, so a duplicate activate endpoint is not introduced.
- (decision) Equipment tree contains compact configuration identity and status only; operational state and analytics are returned by dedicated read models and joined by machineId.
- (decision) Operational overview and current Machine response expose committed effective/current projections and featured current signals without starting or awaiting calculations.
- (decision) General historical endpoints accept either from/to with optional shiftId or one occurrence shiftId plus shiftDate; fake all/day/night shift identifiers are forbidden.
- (decision) Chronometry accepts required shiftDate and optional shiftId; omitted shiftId returns all applicable shift occurrences beginning on that enterprise-local date in one response for the frontend day view.
- (decision) Configuration create endpoints are not given general idempotency keys in MVP; unique code conflicts are deterministic, incident close and cancel are idempotent, and only one active user recalculation per Machine is allowed.
- (constraint) One Spring Boot analytics service and one PostgreSQL own configuration, raw facts, projections and public Analytics API; internal module boundaries must remain separable.
- (constraint) Public reads never synchronously calculate analytics and never expose staging; readers receive the last complete committed projection with currency metadata.
- (constraint) Maximum historical period is 90 days; metric and loss series max 1000 points, telemetry max 720, chronometry max 10000 intervals.
- (constraint) No configuration delete, configuration history, Machine transfer, raw telemetry REST ingestion, generator control, Kafka, production authorization or high-frequency waveform API in this contract.
