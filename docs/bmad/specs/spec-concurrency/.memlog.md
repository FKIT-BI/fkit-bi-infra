---
topic: Конкурентность Analytics и Generator на общей PostgreSQL
goal: Согласовать координацию конфигурационных операций, фоновых расчётов и Generator runs без длительных блокировок на MVP
updated: 2026-10-10T18:18
---

- (direction by user) Пользователь принимает риск last-committed-write-wins для конкурентного редактирования конфигурации; главный приоритет — отсутствие длительных блокировок и скорость с разумным компромиссом стабильности.
- (decision by user) Исторические версии конфигурации и optimistic row version не вводятся; независимые обычные update используют last-committed-write-wins.
- (constraint by user) Конкурентная координация должна быть короткой и ограниченной; не допускать долгих ожиданий write path и блокировки read API.
- (capability by analyst) CAP-1: Система сохраняет целостность конкурентных структурных команд без длительного ожидания; успех — конфликтующий command завершается быстро и ни один пакет не фиксируется частично.
- (capability by analyst) CAP-2: Несколько Analytics instances безопасно обрабатывают расчёты; успех — на одной Machine одновременно публикуется только один work item, а разные Machine обрабатываются параллельно.
- (capability by analyst) CAP-3: Несколько Generator instances не запускают конфликтующие Run; успех — резервирование машин и ограниченного historical capacity проверяется и фиксируется атомарно в PostgreSQL.
- (decision by analyst) Использовать уже согласованные conditional updates, lock владельца Machine/Enterprise, Signal transaction advisory locks, per-machine lease и SKIP LOCKED queue; SKIP LOCKED не использовать как общее чтение данных.
- (decision by analyst) Generator reservation и historical capacity должны быть durable rows в generator schema; machine reservations проверяются при короткой транзакции под transaction-level advisory locks, machine UUID locks приобретаются в стабильном порядке.
- (decision by analyst) Один global historical execution slot на минимальном demo host хранится в PostgreSQL и удерживается до terminal state; Run machine reservations удерживаются до завершения/отмены.
- (decision by user) При потере Generator process с RUNNING Run lease/heartbeat истекает, Run становится FAILED retryable, продолжение использует существующий explicit POST retry и checkpoint; автоматический failover не вводится.
- (decision by analyst) Использовать transaction-scoped try-lock или малый lock timeout для пользовательских reservation/config conflicts; очередь worker-ов использует SKIP LOCKED, transient internal failures получают bounded retry.
- (decision by analyst) Deadlock risk снижается глобальным порядком ресурсов Enterprise, Machine UUID ascending, Signal UUID ascending и затем локальные generator rows; автоматический retry ограничен только безопасными идемпотентными транзакциями.
- (direction by user) Пользователь подтвердил компромисс: принимает stale overwrite risk ради скорости и отсутствия длительных блокировок; транзакционная целостность атомарных операций сохраняется.
- (decision by user) При lease expiry Generator Run в RUNNING переводится в FAILED retryable; продолжение только существующей явной командой retry по checkpoint, автоматический failover не нужен.
- (constraint by analyst) Read API опирается на MVCC committed projections и не участвует в lock protocol фоновых readers; contention в write path ограничивается fail-fast/коротким timeout.
- (decision by analyst) При невозможности быстро claim-нуть пользовательское reservation/config resource операция завершается без partial writes; internal queue consumer пропускает занятую запись и обрабатывает её позднее.
- (assumption by analyst) Generator scheduled runs остаются ограниченными по event-time интервалу через обязательный durationMs/eventTo; open-ended immediate realtime reservation удерживается до terminal Run state.
- (event by analyst) Coherence validation passed: versionless last-committed-write-wins, fail-fast contention, durable reservations, leases, one historical slot and bounded retry form a consistent MVP policy.
- (event by analyst) Preservation validation passed: accepted priority on speed/low blocking, previously agreed DB locks and queue protocol, Generator limits, process-crash retry semantics and residual stale overwrite risk are recorded.
