- (direction) Пользователь подтвердил: generator видит уже созданные Enterprise, ProductionLine, Machine, Component и TelemetrySignal и генерирует raw только по этим объектам; их CRUD остаётся в Analytics API.
- (capability) CAP-1: Пользователь сохраняет переиспользуемый GenerationScenario предприятия для одной или нескольких существующих машин; успех — scenario имеет stable code, ACTIVE/DISABLED и не дублирует equipment CRUD.
- (capability) CAP-2: Пользователь сохраняет неполный disabled scenario и отдельно проверяет готовность; успех — activation/run отклоняются с точными validation issues, пока ownership, line assignment, statuses, signals и behavior types невалидны.
- (capability) CAP-3: Scenario описывает последовательные behavior phases и модели raw-сигналов; успех — поддержаны согласованные numeric, counter, boolean и string/state generators при interval не менее 1000 ms.
- (capability) CAP-4: Каждый GenerationRun воспроизводим независимо от последующих изменений конфигурации; успех — при создании run сохраняется immutable snapshot scenario/equipment/signals и deterministic random seed.
- (capability) CAP-5: Пользователь наблюдает полный операционный lifecycle run; успех — statuses SCHEDULED, QUEUED, RUNNING, STOP_REQUESTED, COMPLETED, STOPPED, CANCELLED и FAILED имеют однозначные переходы.
- (capability) CAP-6: Generator предотвращает конфликтующие запуски; успех — одна machine не участвует одновременно в двух realtime executions, future reservations не пересекаются, multi-machine start атомарен, а на минимальном host активен не более один historical run.
- (capability) CAP-7: Generator публикует только исходные измерения существующих сигналов; успех — batch содержит signalId, observedAt и типизированное value, а official MachineState рассчитывается только analytics.
- (decision) GenerationScenario принадлежит Enterprise и может включать машины разных линий только этого предприятия.
- (decision) Scenario code предлагает frontend; backend проверяет формат/уникальность внутри Enterprise и запрещает изменение code.
- (decision) Новый Scenario создаётся DISABLED, может быть неполным и переводится ACTIVE только после полной validation; физическое удаление отсутствует.
- (decision) Scenario versions не хранятся; run snapshot обеспечивает воспроизводимость и изоляцию от последующих edits/disable.
- (decision) Scenario состоит из ordered phases с code, name, durationMs, optional expectedState, signal behaviors и cycleMode ONCE/LOOP; expectedState диагностический и не записывается в telemetry.
- (decision) Минимальный каталог behavior models: numeric CONSTANT/UNIFORM/NORMAL/RAMP/SINE, COUNTER_RATE with reset, boolean CONSTANT/PULSE/BERNOULLI, string/state CONSTANT/SEQUENCE.
- (decision) Общие signal behavior fields: signalId, generationIntervalMs >=1000, model, typed parameters, noise, missing probability, source quality and optional seed override.
- (decision) Scenario definitions, runs, snapshots, progress and terminal results сохраняются в общей PostgreSQL; analytics остаётся единственным владельцем Flyway migrations.
- (decision) Отдельной Schedule entity в MVP нет: одноразовый будущий запуск представлен SCHEDULED GenerationRun; recurring schedule вне scope.
- (decision) Scheduled run сохраняет snapshot при создании и повторно проверяет current ACTIVE/ownership/readiness перед фактическим start; failed validation не пишет telemetry.
- (decision) Остановка run завершает или откатывает текущий telemetry batch и запрещает новые пакеты; активный run не останавливается из-за последующего disable объекта.
- (constraint) Frontend выбирает equipment через Analytics API; Generator API не предоставляет альтернативный CRUD Enterprise/Line/Machine/Component/Signal.
- (constraint) Generator читает equipment configuration из общей PostgreSQL, но пишет только generator domain и append-only raw telemetry по согласованному contract.
