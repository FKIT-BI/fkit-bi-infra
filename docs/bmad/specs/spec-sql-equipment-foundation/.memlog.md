---
topic: Физическая PostgreSQL-модель конфигурации оборудования и организация Liquibase migrations
updated: 2026-10-10T19:36
---

- (direction) Пользователь утвердил Liquibase вместо Flyway; Analytics остаётся единственным владельцем миграций общей PostgreSQL.
- (decision) Одна физическая PostgreSQL разделяется на схемы equipment, telemetry, analytics, incident и generator; public не содержит доменные таблицы.
- (decision) Liquibase master хранится в fkit-bi-analytics/src/main/resources/db/changelog/db.changelog-master.yaml и явно включает последовательные release changelog без includeAll.
- (decision) YAML используется для оркестрации changelog, а Liquibase formatted SQL — для PostgreSQL DDL, индексов, партиций, функций и ограничений.
- (constraint) Применённые changeset неизменяемы; исправления выполняются новыми globally unique changeset, опасные изменения — forward-only migration.
- (capability) CAP-1: Analytics может детерминированно создать схемы и конфигурационные таблицы на пустой PostgreSQL; success: Liquibase update завершается один раз, повторный запуск не меняет схему.
- (capability) CAP-2: База данных обеспечивает принадлежность Line и Machine одному Enterprise, а Component и Signal одной Machine; success: противоречащие связи отклоняются составными FK.
- (capability) CAP-3: Backend может сохранять Enterprise, ProductionLine, Machine, Component, TelemetrySignal и Shift согласно согласованной доменной модели; success: обязательность, уникальность и локальные CHECK отражают инварианты каждой сущности.
- (capability) CAP-4: Расширяемые семантики сигналов и единицы измерения управляются справочниками; success: неизвестный код не сохраняется, а новый разрешённый код добавляется data changeset без изменения типа колонки.
- (capability) CAP-5: Generator и Analytics используют одну схему данных без совместного владения миграциями; success: generator не запускает Liquibase, а все generator tables создаёт analytics changelog.
- (decision) Закрытые технические наборы хранятся VARCHAR или SMALLINT с CHECK; PostgreSQL native enum не используется.
- (decision) Machine.parameters и Component.parameters хранятся JSONB-массивами; их структурная и лимитная валидация выполняется приложением.
- (decision) Исторические версии конфигурации и optimistic row version в MVP отсутствуют; изменения используют короткие транзакции и блокировки конкретных строк.
- (constraint) Пользовательское физическое удаление конфигурационных сущностей отсутствует; жизненный цикл ограничен ACTIVE и DISABLED.
- (constraint) Идентификаторы UUID генерирует backend; event и audit timestamps используют TIMESTAMPTZ с миллисекундной точностью, локальные границы Shift — TIME(0), validity — DATE.
- (decision) Однократное назначение Machine в Line выполняется условным UPDATE только при line_id IS NULL; проверка циклов Component и сложных пересечений Shift остаётся в доменном сервисе одной транзакции.
- (decision) Минимальные роли: fkit_bi_owner для Liquibase/DDL, fkit_bi_analytics для runtime, fkit_bi_generator для генерации и telemetry append, fkit_bi_monitor для мониторинга.
- (note) Существующий Flyway V1 создаёт только marker table; переход на Liquibase требует отдельного совместимого baseline и удаления Flyway dependency/configuration при реализации.
- (event) Coherence validation passed: capabilities contain intent and success; constraints, non-goals and a demonstrable success signal are defined.
- (event) Preservation validation passed: schema ownership, entity storage, integrity, indexes, migration conventions and Flyway-to-Liquibase transition are retained; wrapper-only conversation phrasing omitted.
- (direction) Пользователь принял упрощённый исправленный SQL architecture baseline.
- (decision) Component parent changes lock the owning Machine before recursive validation; Shift schedule changes lock the owning Enterprise before overlap validation, preventing concurrent write-skew.
- (decision) Signal semantic update and first telemetry use share a serialization protocol backed by durable telemetry.signal_usage; raw retention can never unlock semantic identity.
- (decision) Liquibase runs during Analytics startup using spring.liquibase owner credentials separate from runtime datasource credentials; Analytics readiness remains false until update succeeds.
- (decision) Enterprise timezone storage aligns with OpenAPI at VARCHAR(100).
- (event) Coherence validation passed after simplified concurrency and Liquibase startup amendments.
- (event) Preservation validation passed: the amendments close reviewer findings without adding new services or configuration history.
- (decision by user) Enterprise timezone после первого raw блокируется durable signal_usage, связанной через Signal→Machine→Enterprise; проверка выполняется под enterprise lock.
- (decision by user) Liquibase создаёт platform.schema_release; Analytics и Generator readiness требуют exact supported schema release для MVP.
- (correction by analyst) Compatibility marker размещается в equipment.schema_release, а не в новой platform schema.
- (decision by analyst) Добавлена техническая UNIQUE(machine_id,id) для equipment.telemetry_signal: telemetry.signal_current_value использует denormalized machine_id для чтения current values и composite FK (machine_id,signal_id) к TelemetrySignal, сохраняя owner consistency.
- (decision) No tenant-specific LossReason rows are seeded by Liquibase or Enterprise creation; each Enterprise begins with an empty editable catalog and configures reasons explicitly. Demo fixtures remain outside production migrations.
- (decision) Raw UTC-day partitions for the active 90-day retention window plus seven days ahead are maintained before writer use; creation/drop never runs in ingestion transaction.
- (decision) Existing development DB is not destructively reset or populated from UI/OpenAPI draft samples; the current Flyway marker/history is retained and the first Liquibase business schema starts empty.
