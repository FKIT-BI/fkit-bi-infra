# Правила календаря смен

## Модель Shift

| Поле | Обязательность | Изменяемость | Правило MVP |
| --- | --- | --- | --- |
| `id` | Да | Нет | UUID генерируется backend |
| `enterpriseId` | Да | Нет | Владелец и источник timezone |
| `code` | Да | Нет | Стабильный код, уникальный внутри Enterprise |
| `name` | Да | Да | Отображаемое имя |
| `startLocalTime` | Да | До первого использования | Локальное время с минутной точностью |
| `endLocalTime` | Да | До первого использования | Локальное время с минутной точностью |
| `validFrom` | Да | До первого использования | Включительная локальная дата начала действия |
| `validTo` | Нет | Ограниченно | Исключительная локальная дата окончания действия |
| `sortOrder` | Да | Да | Неотрицательное целое; затем сортировка по `code` |
| `status` | Да | Да | Собственный `ACTIVE` или `DISABLED` |
| `createdAt`, `updatedAt` | Да | Нет | Технические UTC timestamps ответа |

`day` и `night` могут быть пользовательскими кодами, но не имеют системной семантики. Код предлагает frontend; backend проверяет формат, уникальность и неизменяемость.

После первого связанного измерения или агрегата `startLocalTime`, `endLocalTime` и `validFrom` блокируются. `validTo` можно установить или приблизить только так, чтобы новый диапазон не исключал уже связанные `shiftDate`; иначе backend возвращает `409 SHIFT_SCHEDULE_LOCKED`.

## Период действия и длительность

Validity является полуоткрытым диапазоном локальных дат:

```text
validFrom <= shiftDate < validTo
```

При `validTo = null` верхней границы нет.

Длительность экземпляра определяется так:

| Условие | Окончание |
| --- | --- |
| `endLocalTime > startLocalTime` | В ту же локальную дату |
| `endLocalTime < startLocalTime` | В следующую локальную дату |
| `endLocalTime = startLocalTime` | Через 24 локальных часа |

Каждый интервал полуоткрытый: начало включено, окончание исключено. Поэтому общая граница двух соседних смен принадлежит следующей смене.

## ShiftOccurrence

`ShiftOccurrence` является вычисляемым значением, а не таблицей:

```text
ShiftOccurrenceKey = (shiftId, shiftDate)
```

`shiftDate` — локальная дата начала экземпляра. Для смены `20:00–08:00` событие в `03:15` относится к экземпляру с датой предыдущего дня.

Алгоритм для `observedAt`:

1. Определить `Enterprise` машины и его IANA timezone.
2. Перевести `observedAt` instant в локальные дату и время предприятия.
3. Для дневной смены использовать текущую локальную дату как кандидата `shiftDate`.
4. Для смены через полночь использовать предыдущую дату, если локальное время раньше `endLocalTime`, иначе текущую.
5. Проверить попадание `shiftDate` в validity определения.
6. Построить start/end как zoned boundaries и проверить `start <= observedAt < end`.
7. Вернуть единственное совпадение либо `shiftId = null`, если событие находится в разрешённом промежутке.

Согласованная конфигурация не может дать два совпадения.

## Пересечения и промежутки

Для любых Shift одного Enterprise с пересекающимися validity-диапазонами backend запрещает пересечение их ежедневных интервалов. Правило применяется независимо от текущего `status`, чтобы исторический backfill оставался однозначным.

Промежутки разрешены. События в них:

- остаются в общей аналитике предприятия, линии и машины;
- не входят в shift-scoped агрегаты;
- получают `shiftId = null` и `shiftDate = null` в соответствующей расчётной проекции.

## Изменение расписания

После использования смены новое расписание создаётся последовательностью:

1. Установить старой Shift допустимый `validTo`.
2. Создать новую Shift с новым `id`, новым уникальным `code` и `validFrom`, равным дате начала нового расписания.
3. Проверить отсутствие временных пересечений со всеми применимыми Shift предприятия.
4. Сохранить старые агрегаты с прежними `shiftId` и `shiftDate`.

Имя новой смены может совпадать со старым. Исторические и будущие данные выбирают определение по event time, а не по времени записи или текущему статусу.

## ACTIVE и DISABLED

`ACTIVE` разрешает выбирать Shift в новых operational-настройках и generator runs. `DISABLED` исключает её из таких списков, но:

- не удаляет определение и агрегаты;
- не меняет уже назначенные `shiftId` и `shiftDate`;
- разрешает историческое чтение;
- разрешает backfill и перерасчёт внутри validity.

Чтобы отключённая смена не продолжала применяться к будущему event time, перед отключением ей задают конечный `validTo`. Сам алгоритм event-time назначения использует validity и границы, а не `status`.

## DST

Локальные границы разрешаются через `Enterprise.timezone` одинаково для realtime и backfill:

- если локальное время попало в DST gap и не существует, граница сдвигается к первому допустимому instant после разрыва;
- если локальное время повторяется при DST overlap, выбирается более раннее UTC-смещение;
- одна и та же локальная граница соседних смен разрешается одинаково, поэтому искусственный разрыв или наложение между ними не возникает.

Изменение `Enterprise.timezone` после появления временных эксплуатационных данных запрещено соседней спецификацией базовой конфигурации.

## Хранение и запросы

Raw telemetry хранит исходный `observedAt`, но не обязана дублировать `shiftId`. Подготовленные shift-aware интервалы или агрегаты сохраняют `shiftId` и `shiftDate` для быстрого чтения и устойчивой исторической группировки.

Команды конфигурации:

```text
GET  /api/enterprises/{enterpriseId}/shifts
POST /api/enterprises/{enterpriseId}/shifts
GET  /api/shifts/{shiftId}
PUT  /api/shifts/{shiftId}
PUT  /api/shifts/{shiftId}/status
```

Shift-specific аналитика использует:

```text
shiftId + shiftDate     — одна occurrence
shiftId + from + to     — occurrences одной Shift за период
```

Общая аналитика без фильтра смены не передаёт фиктивный `shiftId=all`. Аналитические методы, явно работающие в разрезе смены, требуют реальный `shiftId`; литералы `day`, `night` и `all` не принимаются.
