topic: Конфигурация телеметрических сигналов и границы оптимизированной обработки
updated: 2026-10-08T23:16
---

- (direction) Пользователь согласовал модель TelemetrySignal и потребовал снизить частоту обработки, оптимизировать пакетную вставку, последующий поиск и аналитику.
- (capability) CAP-1: Пользователь конфигурирует типизированный TelemetrySignal машины, опционально относя его к Component; успех — валидная конфигурация однозначно задаёт физический тип, поведение, семантику и единицу.
- (capability) CAP-2: Система интерпретирует GAUGE, COUNTER и STATE по разным правилам; успех — поддерживаются только согласованные сочетания signalKind и valueType.
- (capability) CAP-3: Пользователь задаёт ожидаемую частоту, устаревание и физические границы без потери аномальных raw; успех — freshness вычисляется детерминированно, а значение вне диапазона сохраняется с качеством.
- (capability) CAP-4: Пользователь управляет жизненным циклом сигнала без переинтерпретации истории; успех — идентичность стабильна, смысловые поля блокируются после первого raw, DISABLED сохраняет историю.
- (capability) CAP-5: Телеметрия принимается и анализируется независимо от пользовательского чтения; успех — пакетная запись не выполняет аналитику синхронно, а frontend читает подготовленные проекции с ограниченной задержкой.
- (decision) TelemetrySignal является конфигурацией канала; TelemetryMeasurement является отдельным неизменяемым raw-фактом.
- (decision) Signal принадлежит одной Machine, может ссылаться только на Component той же Machine и имеет code, уникальный внутри Machine.
- (decision) MVP valueType: DOUBLE, LONG, BOOLEAN, STRING; signalKind: GAUGE, COUNTER, STATE с нормативной матрицей совместимости.
- (decision) semanticCode является строковым кодом из расширяемого backend-каталога; CUSTOM требует customSemanticCode, чтобы OpenAPI enum не блокировал расширение.
- (decision) Роль сигнала в расчёте не хранится флагом requiredForState: декларативное StateRule явно ссылается на нужные сигналы.
- (decision) Протокольный sourceAddress не входит в TelemetrySignal; generator и будущие адаптеры владеют сопоставлением источника с signalId.
- (decision) expectedIntervalMs и staleAfterMs nullable; первый описывает ожидание от источника, второй — freshness, а частота генерации задаётся отдельно сценарием generator.
- (decision) validMin/validMax описывают физически допустимый диапазон; выход за него не отбрасывает raw, а влияет на quality.
- (decision) id, machineId и code неизменяемы; после первого raw также неизменяемы valueType, signalKind, semanticCode и unitCode; componentId меняется только в пределах той же Machine.
- (decision) Сигнал управляется ACTIVE/DISABLED без физического удаления; активный generator run продолжает работу по snapshot, новые конфигурации не выбирают DISABLED.
- (constraint) Backend не создаёт отдельную задачу обработки на каждый Signal и не считает аналитику в транзакции ingestion.
- (decision) Generator передаёт измерения пакетами до 1000 строк либо сбрасывает пакет каждые 1–2 секунды; историческая загрузка сможет применять более крупные внутренние пакеты.
- (decision) Текущие значения обновляются ориентировочно каждые 5 секунд, состояния каждые 5–10 секунд, минутные агрегаты каждые 30 секунд, сменные показатели раз в минуту и при закрытии смены.
- (decision) Frontend использует подготовленные read-модели; raw допускается только для ограниченного диагностического диапазона, а выбор физической проекции выполняет backend.
- (constraint) В MVP интервал генерации не быстрее одной секунды; высокочастотные waveform и осциллограммы вынесены за scope.
- (decision) Конфигурационный API использует коллекцию /api/machines/{machineId}/telemetry-signals и ресурс /api/telemetry-signals/{signalId}, включая отдельную смену status.
