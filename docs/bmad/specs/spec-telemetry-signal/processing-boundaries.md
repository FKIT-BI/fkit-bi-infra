# Границы обработки и чтения

## Разделение частот

Частота создания raw, пакетной отправки, фонового расчёта и обновления UI не совпадает. `expectedIntervalMs` описывает ожидание от источника, а `generationIntervalMs` принадлежит сценарию generator.

Рекомендуемый профиль MVP:

| Данные | Ориентир генерации |
| --- | ---: |
| Температура, давление, мощность | 5–10 секунд |
| Итоговое значение вибрации | 1–5 секунд |
| Производственный счётчик | 5–10 секунд |
| Медленно меняющийся уровень | 15–30 секунд |
| Дискретное состояние и аварийный флаг | При изменении с периодическим heartbeat |

Интервал меньше одной секунды и waveform не входят в MVP. Порог `staleAfterMs`, если задан, рекомендуется выбирать не меньше трёх ожидаемых интервалов, но нормативная проверка требует только `staleAfterMs >= expectedIntervalMs` при наличии обоих значений.

## Ingestion boundary

Generator и будущие источники передают массивы измерений. Обычный пакет ограничивается 1000 измерениями либо сбрасывается каждые 1–2 секунды. Один пакет записывается одной транзакцией с batch insert. Исторический внутренний режим может использовать более крупные пакеты после отдельного нагрузочного теста.

Приём выполняет только транспортную и доменную валидацию, типизацию, проверку идемпотентности и сохранение raw. В его транзакцию не входят состояние машины, временные интервалы, сменные показатели или rollup.

Точный DTO события, ключ идемпотентности, `observedAt/receivedAt`, quality, late data, SQL-партиционирование и индексы определяет спецификация raw telemetry.

## Расчётные ориентиры MVP

| Проекция | Ориентир обновления |
| --- | ---: |
| Последнее значение сигнала | До 15 секунд |
| Текущее состояние машины | До 20 секунд |
| Минутный rollup сигнала | До 120 секунд |
| Текущий итог смены | Раз в минуту |
| Закрытая смена | После обработки всех известных данных смены |

Все сигналы обрабатываются общими пакетными workers по checkpoint и диапазонам event time; отдельные задачи на Signal отсутствуют.

## Контракт frontend

Frontend не собирает показатели из raw и не выбирает физическую таблицу. Он запрашивает предметную read-модель с периодом и гранулярностью, а backend выбирает текущую проекцию, точные интервалы или подходящий rollup.

Основные виды подготовленных данных:

- последнее значение сигнала и его freshness;
- текущее состояние машины;
- интервалы состояний;
- временной ряд сигнала с заданной гранулярностью;
- итог машины, линии или предприятия за occurrence смены либо период.

Raw разрешается только для короткой диагностической выборки с обязательными `signalId`, `from`, `to` и серверным пределом точек. Обычные dashboard и историческая аналитика читают подготовленные данные. Все ответы аналитики сообщают `dataThrough` или эквивалентную границу актуальности расчёта.
