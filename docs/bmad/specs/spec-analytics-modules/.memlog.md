---
topic: Модульные границы приложений Analytics и Generator
updated: 2026-10-10T19:39
---

- (capability) CAP-1: Команда может реализовать Analytics как модульный монолит и затем извлечь отдельные сервисы без переноса бизнес-логики между слоями; success — модули имеют явных owners, application ports и schema/data ownership.
- (decision) Для MVP модульность реализуется Java packages в одном Gradle/Maven application, без отдельных Gradle subprojects; физический service split откладывается, application ports остаются границей будущего извлечения.
- (decision) Analytics packages: identity/auth, equipment, telemetry-ingestion, state-processing, incidents, analytics-query и maintenance; Generator packages: scenario-control, run-execution и telemetry-sink.
- (constraint) HTTP/API adapters call application services; domain modules do not call another module private repository. Cross-module work uses narrow application ports; shared package contains only stable technical primitives, not duplicated domain models.
- (decision) Spring @Transactional use-case boundaries may atomically cover explicitly approved tables across logical schemas (telemetry raw+batch+hint, incident+dirty work, projection publication); no distributed transactions or network calls occur inside them.
- (decision) Schedulers/workers run inside Analytics and claim durable PostgreSQL work via expiring leases/SKIP LOCKED; no correctness-critical queue or lock exists only in process memory.
- (event) Coherence pass: package modularity is simpler than build-level modules while preserving ownership, API boundaries, PostgreSQL coordination and future extraction seams.
