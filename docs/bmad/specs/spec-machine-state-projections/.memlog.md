- (direction) Пользователь согласовал state projections, minute-aligned dirty ranges, background staging replacement, simple state-only intervals, PostgreSQL deadlines and user-selected PERIOD/ALL recalculation.
- (capability) CAP-1: Система публикует current state и непрерывную interval history от активации Machine; успех — timeline внутри coverage не имеет дыр/пересечений, а current читается одной строкой.
- (capability) CAP-2: Новые и late measurements создают удобные диапазоны актуализации; успех — dirty windows расширяются до UTC minute boundaries, coalesce per machine и пересчитываются до current dataThrough.
- (capability) CAP-3: Фоновый перерасчёт не показывает частичный результат; успех — результат готовится в staging, валидируется и коротко заменяет active range, пока frontend читает старую complete timeline.
- (capability) CAP-4: Time-based transitions выполняются без нового measurement; успех — одна ближайшая deadline row на Machine запускает stale, activation, release и offline evaluation с точным effectiveFrom.
- (capability) CAP-5: Пользователь запускает asynchronous PERIOD или ALL recalculation; успех — PERIOD нормализуется/расширяется, ALL охватывает coverageFrom..dataThrough, job имеет наблюдаемый lifecycle и атомарную публикацию.
- (capability) CAP-6: Несколько workers безопасно рассчитывают разные machines; успех — per-machine lease и SKIP LOCKED исключают одновременную публикацию одной Machine и позволяют recovery после crash.
- (decision) coverageFrom immutable equals first Machine activation; before it state is undefined, after it absence of telemetry yields OFFLINE.
- (decision) Historical coverage is half-open [coverageFrom,dataThrough); dataThrough is an exclusive UTC minute boundary covering all batches known to the worker at publication and may later be revised by late data.
- (decision) Dirty from/to expand outward to UTC minute boundaries, merge per Machine, extend left to stable evaluator context and recalculate through current dataThrough.
- (decision) machine_state_interval is state-only: machineId, effectiveFrom, nullable effectiveTo, state, detectedAt, calculatedAt; intervals split only when state changes and adjacent equal states merge.
- (decision) machine_current_state stores state, stateSince, matchedRuleId, evaluationQuality, lastTelemetryObservedAt, dataThrough, calculatedAt and recalculating.
- (decision) Exact state transition timestamps keep millisecond precision; minute alignment applies only to calculation/coverage ranges.
- (decision) Background result is written to job staging, checked for coverage/gaps/overlaps, then replaces active interval range with current state and checkpoints in one short MVCC transaction.
- (decision) One machine_evaluation_deadline row per Machine stores nearest stale/rule activation/rule release/offline deadline; worker leases due rows with FOR UPDATE SKIP LOCKED and schedules the next deadline.
- (decision) For equal observedAt, signal snapshot resolves by observedAt, ingestBatchId, ordinal and evaluator runs once after all values at that timestamp are assembled.
- (decision) Recalculation API accepts PERIOD from/to or ALL; one user recalculation per Machine may be active, conflict returns 409, statuses PENDING/RUNNING/SUCCEEDED/FAILED.
- (decision) During recalculation old projection remains readable with recalculating=true; realtime ingestion/current processing continues and partial staging data is never exposed.
- (constraint) State intervals do not store or split by shiftId; shift-aware metric buckets split durations later.
- (constraint) Frontend does not wait for recalculation and reads only committed current/timeline projections with currency metadata.
- (decision) After rule change current state is evaluated with current rules; historical intervals are recalculated only for a user-requested PERIOD or ALL, using the current configuration because versions do not exist.
- (event) Coherence validation passed: six capabilities have intent and testable success; coverage, state-only intervals, deadline scheduling, staging publication and manual recalculation are mutually consistent.
- (event) Preservation validation passed: all eight resolved questions, minute boundaries, exact timestamps, equal-time ordering, PERIOD/ALL API, leases and frontend behavior are present; deferred API pagination/retention details remain explicit non-goals.
- (event) Spec finalized after explicit user acceptance; no open questions remain inside state projections/recalculation block.
