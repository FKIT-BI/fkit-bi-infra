- (direction) Пользователь согласовал MachineStateConfig, StateRule evaluator и детализированный набор операторов сравнения и поручил оформить spec.
- (capability) CAP-1: Пользователь атомарно задаёт одну текущую MachineStateConfig; успех — backend валидирует default state, offline timeout и весь rule AST до сохранения.
- (capability) CAP-2: Пользователь выражает условия типизированным AST без исполняемого кода; успех — ALL, ANY, NOT и COMPARE поддерживают только совместимые signal-to-literal операции.
- (capability) CAP-3: Evaluator детерминированно выбирает состояние по unique priority, delay и hysteresis; успех — OFFLINE предшествует rules, higher priority preempts после activation delay, иначе применяется default state.
- (capability) CAP-4: Evaluator обрабатывает stale/bad input трёхзначной логикой; успех — UNKNOWN не активирует rule, освобождает active rule после release delay и отражается DEGRADED quality.
- (capability) CAP-5: Система различает event-time переход и время обнаружения; успех — effectiveFrom учитывает непрерывное condition delay, detectedAt фиксирует processing time и допускает historical correction.
- (capability) CAP-6: Frontend может проверить configuration без сохранения и объяснить результат; успех — validate endpoint возвращает структурированные ошибки, current result содержит matchedRuleId и evaluationQuality.
- (decision) MachineStateConfig: machineId, defaultState default IDLE, offlineAfterMs default 60000, rules JSON, updatedAt; одна current configuration без версий.
- (decision) Rule fields: id, name, unique priority, targetState, enterCondition, optional exitCondition, activationDelayMs and releaseDelayMs.
- (decision) User rules output RUN, IDLE, DOWN, PLANNED_STOP or SETUP; OFFLINE is reserved system state evaluated first.
- (decision) AST nodes are ALL, ANY, NOT and COMPARE; signal references use signalId and cannot cross Machine boundary.
- (decision) Operators are EQ, NE, GT, GTE, LT, LTE, BETWEEN and IN with strict type compatibility; NOT expresses negative set/range conditions.
- (decision) DOUBLE EQ/NE require positive finite tolerance in signal units; EQ is abs(actual-expected)<=tolerance and NE is greater; no rounding or unit conversion.
- (decision) BETWEEN is inclusive; strict bounds use ALL with GT/LT; IN is exact, limited to 1..50 unique LONG or STRING literals.
- (decision) String comparisons are case-sensitive without trim or normalization; missing/stale/unusable input makes every comparison including NE return UNKNOWN.
- (decision) Three-valued logic: NOT UNKNOWN=UNKNOWN; ALL false if any false, true if all true, otherwise unknown; ANY true if any true, false if all false, otherwise unknown.
- (decision) Activation requires continuous TRUE; active rule release uses continuous exitCondition TRUE or enterCondition FALSE/UNKNOWN when exit is absent; interruption resets the timer.
- (decision) Evaluation result includes state, effectiveFrom, detectedAt, matchedRuleId nullable and evaluationQuality COMPLETE or DEGRADED.
- (decision) Configuration limits: maximum 20 rules, AST depth 10 and total 100 AST nodes; no arithmetic, regex, scripts, signal-to-signal comparisons or temporal/window operators.
- (decision) API: GET/PUT machine state-configuration and POST validate; PUT atomically replaces current JSON configuration, validated/compiled evaluator is cached.
- (constraint) Machine activation requires valid state configuration with at least one rule, all referenced signals on the machine, staleAfterMs on each input and positive offlineAfterMs.
- (event) Coherence validation passed: six capabilities have intent and testable success; operator typing, UNKNOWN, priority, delay, hysteresis, OFFLINE and default semantics do not conflict.
- (event) Preservation validation passed: configuration model, full AST/operator contract, DOUBLE tolerance, API, activation validation, result metadata and seven examples are present; wrapper-only dialogue omitted.
- (event) Spec finalized after explicit user acceptance; no open questions remain inside StateRule block.
