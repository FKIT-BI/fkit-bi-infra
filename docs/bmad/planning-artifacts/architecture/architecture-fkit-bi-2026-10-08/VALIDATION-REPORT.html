CHANGES REQUIRED

FKIT BI: проверка SQL и telemetry architecture

Базовая архитектура подходит для MVP: одна PostgreSQL, нормализованное equipment-ядро, append-only raw, суточные UTC-партиции и чтение готовых проекций. Смена БД, Kafka или TSDB не требуется. Перед DDL нужно закрыть несколько конкретных гонок и operational gaps.

Что уже правильно

Нормализация

Owner IDs и составные FK оправданы; справочники semantic/unit нормализованы; JSONB ограничен display-only параметрами.

Hot path

Batch header + typed raw rows, отсутствие per-row FK/UPSERT и один signal/time index соответствуют принятой нагрузке.

Чтение

MVCC и готовые projections отделяют frontend от ingestion и перерасчётов.

Обязательные поправки до реализации

01Partition lifecycle

Узкие owner-owned routines, общий advisory lock, короткий lock timeout, создание заранее и retry retention без DDL в insert path.

02Batch hash

payload_hash связывает idempotency key с содержимым; несовпадающий retry становится явной ошибкой.

03Durable dirty handoff

Raw и recalculation hints фиксируются одной транзакцией; retention ждёт consumption и публикацию проекций.

04Historical window

Historical ограничен активными 90 сутками; полностью истёкшие UTC-дни удаляются только без jobs/leases.

05First-use marker

Неудаляемый signal_usage сохраняет факт первого raw и сериализует первую запись с изменением семантики.

06Aggregate locks

Component tree блокируется на Machine, Shift schedule — на Enterprise до проверок циклов и пересечений.

07Physical codes

Фиксируются числовые mapping; quality хранится один раз, без дублирующих SOURCE_* flags.

08Bounded storage

Ключи и string values ограничены; ingest headers очищаются chunks с индексом и vacuum monitoring.

09Bulkheads

Query получает зарезервированные connections; historical и workers ограничены permits и disk preflight.

10Startup contract

One-shot Liquibase owner → Analytics runtime → schema-ready → Generator compatible readiness.
