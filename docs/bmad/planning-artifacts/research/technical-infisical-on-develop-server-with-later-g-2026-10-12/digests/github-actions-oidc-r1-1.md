# Digest — GitHub Actions retrieval through OIDC

- **Claim:** The official Infisical Secrets Action supports both Cloud and self-hosted instances through an explicit `domain` input, OIDC authentication, secret selection by project/environment/path, and exporting values as runner environment variables or a file. **Source:** Infisical, `secrets-action` README, accessed 2026-10-12, https://github.com/Infisical/secrets-action. **Confidence:** high (primary integration source).
- **Claim:** OIDC requires workflow/job `id-token: write`; it allows the runner to request a signed GitHub identity token, and by itself does not grant GitHub write access. Infisical machine identity can bind the trusted issuer, audience, subject/claims and project permissions. **Sources:** Infisical, GitHub OIDC guide, accessed 2026-10-12, https://github.com/Infisical/infisical/blob/main/docs/documentation/platform/identities/oidc-auth/github.mdx; GitHub Docs, OIDC reference, accessed 2026-10-12, https://docs.github.com/en/actions/reference/security/oidc. **Confidence:** high.
- **Claim:** The workflow must contact the configured Infisical `domain` to exchange the GitHub OIDC token and retrieve values. Therefore a GitHub-hosted `ubuntu-latest` runner needs public HTTPS reachability to the develop server; an Infisical service bound only to localhost/private LAN will not work for this runner. This is an architecture inference from the documented protocol. **Sources:** Infisical integration README and OIDC guide above; GitHub OIDC reference. **Confidence:** high.
- **Claim:** Secrets fetched at runtime still become available to subsequent steps on the GitHub-hosted runner. Replacing GitHub Secrets removes long-lived secret storage there, but does not keep runtime values off the runner. GitHub advises least privilege, log review, action auditing, and rotating any value exposed in logs. **Source:** GitHub Docs, secure use reference, accessed 2026-10-12, https://docs.github.com/en/actions/reference/security/secure-use. **Confidence:** high.
- **Implementation note:** Do not fetch a whole project/environment into every job. Create separate machine identities per repo/use-case with the narrowest possible path/environment permissions, and fetch only the names each job needs. Pin the third-party action to a verified full commit SHA once its chosen release is established.
