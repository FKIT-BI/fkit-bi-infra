# Технический анализ: Infisical на develop-сервере

**Решение, для которого подготовлен анализ:** выбрать безопасный и простой поэтапный запуск: сначала разместить Infisical на Dev и проверить интерфейс и получение секретов, затем подключать GitHub Actions через OIDC.

## Краткий вывод

**Рекомендация:** идти в два этапа. Сначала развернуть Infisical как self-hosted сервис для демо на develop VM и проверить вход через браузер и получение безвредного тестового секрета. Только после этого менять GitHub Actions, чтобы они получали выбранные значения во время запуска через OIDC. Официальный action поддерживает собственный домен и OIDC; GitHub-hosted runner сможет работать с ним, если сервис доступен по HTTPS. [4][5][6]

Есть важная оговорка о приватности: в текущем исходном коде Infisical продуктовая телеметрия и загрузка объявлений включены по умолчанию, хотя сервер self-hosted. Их нужно явно отключить и проверить исходящие соединения. Само размещение на своём сервере не доказывает, что никакой трафик не уходит поставщику. [3]

Секреты, пользователи и проекты хранятся в PostgreSQL Infisical; для расшифровки восстановленной базы нужен постоянный ключ шифрования. Хранить его следует отдельно от базы, в защищённом операторском хранилище, и отдельно резервировать. [1][2]

**Главное ограничение внедрения:** текущим GitHub-hosted runners нужен публичный HTTPS-адрес с доверенным сертификатом. Действующий сертификат не включает предполагаемый адрес `secrets.kitexp.ru`, и это имя сейчас не резолвится. До проверки OIDC нужно добавить DNS-запись и HTTPS-маршрут Nginx. Этот отчёт помогает принять решение и спланировать этапы; сам деплой здесь не выполнялся.

## 1. Граница данных и эксплуатация self-hosted сервиса

В описанной Infisical конфигурации Compose используются само приложение, PostgreSQL и Redis. PostgreSQL — постоянный источник данных, Redis отвечает за кэширование и фоновые задачи. Одноузловой Compose представлен как вариант для тестирования или небольшого развёртывания, а не как отказоустойчивая архитектура. [1][2] Уверенность: средняя — это рекомендации производителя, а не независимые измерения эксплуатации.

Ключ шифрования критически важен для восстановления: одной резервной копии базы недостаточно, чтобы прочитать секреты. Базу Infisical и ключ нужно резервировать раздельно, под защитой, и проверить восстановление до того, как хранилище станет единственной копией важных учётных данных. [2] Уверенность: средняя.

В текущих настройках сервера `TELEMETRY_ENABLED` по умолчанию равен `true` и настроен адрес PostHog; `ANNOUNCEMENTS_ENABLED` тоже включён. В комментарии к настройке указано, что администратор self-hosted сервера может отключить исходящие запросы объявлений. Сбор метрик OpenTelemetry управляется отдельной настройкой, выключенной по умолчанию, поэтому её одной недостаточно, чтобы отключить продуктовую телеметрию. [3] Уверенность высокая для изученных значений конфигурации. Полный перечень исходящих запросов и их содержимое не аудировались — это остаётся открытым вопросом. Для демо явно отключить и телеметрию, и объявления, затем наблюдать исходящий трафик во время проверки тестового секрета.

## 2. Интеграция с GitHub Actions и граница безопасности

Официальный Infisical Secrets Action принимает собственный `domain`, поддерживает OIDC и может экспортировать выбранные секреты в переменные среды или файл. Для OIDC настраивается машинная учётная запись с issuer, audience, subject/claims и правами, соответствующими целевому workflow. Публичный сторонний проект также документирует использование self-hosted Infisical из GitHub Actions по OIDC; это подтверждает практическую применимость схемы, но не заменяет нашу проверку. [4][5][7] Уверенность высокая для поддержки интеграции; средняя для независимого примера.

Чтобы запросить OIDC-токен, GitHub требует разрешение `id-token: write` для job. Оно разрешает выпуск токена, но само по себе не даёт право записывать в репозиторий. Workflow передаёт короткоживущий токен GitHub в Infisical, после проверки получает разрешённые значения. [5][6] Поскольку текущие runners — `ubuntu-latest`, адрес Infisical должен быть публично доступен по HTTPS. Это архитектурный вывод из описанного обмена; уверенность высокая.

OIDC избавляет от необходимости хранить в GitHub долгоживущий секрет доступа к Infisical, но **не** скрывает полученные значения от GitHub-hosted runner: они доступны последующим шагам workflow. GitHub рекомендует выдавать минимальные права, проверять actions и журналы, а при утечке секрета — менять его. [4][6] Поэтому получать следует только нужные деплойному шагу секреты, после проверок и сборки, а машинные учётки ограничить одним репозиторием и нужным путём/окружением.

## 3. Последовательность внедрения и локализация риска

На первом этапе изолировать Infisical от базы данных BI: выделить ему собственные PostgreSQL и Redis, постоянный том данных и не публиковать порты базы/кэша наружу. Вход снаружи — только через HTTPS reverse proxy. Зафиксировать проверенную версию образа, защитить и резервировать ключ шифрования, отключить необязательную телеметрию/объявления и создать тестовый проект/окружение с фиктивным секретом-canary. [1][2][3]

На втором этапе подключать выдачу по OIDC только в доверенных deploy jobs, оставив PR-проверки без секретов. Начать с одного репозитория/workflow и одного некритичного секрета, проверить журналы и события аудита, затем расширять интеграцию. Оставить текущий механизм GitHub Secrets как возможность отката, пока новый workflow не пройдёт полный деплой.

Приложение Infisical, база и кэш добавят нагрузку на сервер с демо-стендом BI. Доступные ресурсы хоста здесь не измерялись. До запуска проверить свободную память, место на диске и потребление контейнеров; остановиться, если BI уже близок к пределу. При отказе или компрометации общей VM пострадают и демо, и хранилище секретов. Это допустимый риск только для демо, а не гарантия изоляции уровня production.

## Общий вывод

Self-hosted размещение даёт больше контроля над постоянной базой секретов. GitHub-hosted runners оставляют CI проще в эксплуатации, но рабочие секреты всё равно попадут в среду временного runner. Эти варианты совместимы, если разделить границы доверия: администраторские и DB-секреты Infisical хранить на VM, наружу выставить только HTTPS API/UI, а доступ по OIDC дать лишь выбранным deploy jobs. [2][4][6]

## Рекомендации

1. **Развернуть демо в два этапа.** Сначала установить и проверить UI и получение тестового секрета; после приёмки — подключать Actions по OIDC. Выполнимость подтверждается документацией Infisical и GitHub. [4][5][6]
2. **Использовать отдельное имя и TLS-маршрут.** `secrets.kitexp.ru` — пока только вариант: направить его A-запись на develop VM, добавить сертификат и маршрут Nginx. До изменения DNS или TLS подтвердить точное имя. Публичный HTTPS нужен текущему hosted runner; конкретный hostname — решение развёртывания.
3. **Явно отключить необязательные исходящие функции и проверить трафик.** Установить `TELEMETRY_ENABLED=false`, `ANNOUNCEMENTS_ENABLED=false`, оставить `OTEL_TELEMETRY_COLLECTION_ENABLED=false`. Проверить исходящие соединения, а не делать вывод об их отсутствии лишь из self-hosted режима. Настройки по умолчанию проверены с высокой уверенностью, полный перечень оставшихся исходящих запросов — со средней. [3]
4. **Хранить данные восстановления отдельно от базы.** Защитить резервную копию PostgreSQL и `ENCRYPTION_KEY`; проверить восстановление. Уверенность средняя, на основании документации развёртывания. [2]
5. **Не переносить секреты механически все сразу.** Ключ шифрования Infisical, доступ к его базе и первичная администраторская учётка останутся операторскими bootstrap-секретами. В GitHub переносить только реальные долгоживущие значения, необходимые доверенным deploy jobs; оставить встроенный краткоживущий `GITHUB_TOKEN` и не выдавать машинным учёткам лишние права. [4][6]

## Открытые вопросы

- Какое точное имя хоста использовать и можно ли добавить A-запись в текущей панели DNS?
- Сколько памяти и диска доступно на develop VM при типичной нагрузке BI?
- Какие ещё компоненты выбранной версии Infisical, кроме телеметрии и объявлений, инициируют исходящие соединения? Проверить на тестовом экземпляре и по сетевым логам.
- Вторая стадия: verify-job infra-репозитория клонирует приватные репозитории Analytics и Generator. Нужно решить, как оставить ему доступ на чтение, не открывая секреты коду из pull request. Не заменять эту задачу безграничными OIDC-правами.
- Какие учётные данные переносить первыми? GitHub Secrets невозможно прочитать обратно; значения нужно вручную внести в новое хранилище из защищённого источника.
